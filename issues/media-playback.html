1System fullscreen video player: The WebAVPlayerController backdoor

When an iOS user taps the fullscreen button on a web video in Safari, iOS displays the standard system media player with native transport controls, scrubbing physics, audio track selectors, subtitle menus, and playback speed buttons. For regular iOS apps, this interface is provided by AVKit's public AVPlayerViewController. However, AVPlayerViewController is architected strictly around Apple's monolithic AVPlayer class: an app passes an AVPlayer instance, and AVKit handles playback, demuxing, and user interface controls internally.

Modern browser engines do not decode video inside a monolithic player object in the application process. WebKit decodes web video inside a sandboxed GPU process and delivers decoded video frames directly to a display layer (an AVSampleBufferDisplayLayer or WebAVPlayerLayer). Because the public AVPlayerViewController accepts no custom frame source or sample stream, WebKit cannot pass an AVPlayer. Instead, WebKit drives Apple's system fullscreen player through an elaborate private backdoor: it defines WebAVPlayerController, and at runtime dynamically allocates a new Objective-C class pair derived from the private internal class AVPlayerController (named WebAVPlayerControllerForwarder_AVKitCompatible). WebKit then feeds this synthetic controller into AVPlayerViewController via the private SPI initializer -[AVPlayerViewController initWithPlayerLayerView:] and calls private methods such as enterFullScreenAnimated:completionHandler:.

How Safari / WebKit does it

  • WebAVPlayerController tracks playback rate, seekable time ranges, and live stream status from WebCore's media element.
  • In WebAVPlayerController.mm, WebKit invokes objc_allocateClassPair on PAL's private AVPlayerController class singleton, adds ivars, overrides unknown methods, and registers WebAVPlayerControllerForwarder_AVKitCompatible so that AVKit's internal Swift runtime checks (as! AVPlayerController) succeed without crashing.
  • In VideoPresentationInterfaceAVKitLegacy.mm, WebKit initializes AVPlayerViewController using the private initializer initWithPlayerLayerView:, sets AVPlayerViewControllerFullScreenBehaviorHostContentInline, and drives transitions via private enterFullScreenAnimated:completionHandler:.
  • WebKit implements the private protocol AVPlayerViewControllerDelegate_WebKitOnly to intercept fullscreen exit events (pinch gestures, done button taps, PiP transitions).

What a BrowserEngineKit browser can do

  • Third-party engines cannot subclass or instantiate the private AVPlayerController class, nor call private AVPlayerViewController SPIs, because doing so relies on non-exported framework symbols and private headers that violate App Store review rules.
  • If an alternative engine decodes video with its own pipeline (such as Chromium or Gecko decoding video in a rendering extension and rendering to an AVSampleBufferDisplayLayer or Metal texture via IOSurface), it cannot use the system fullscreen player.
  • The engine must draw its own fullscreen video controls overlay in HTML or native UIKit. While a custom UI can mimic iOS controls, it loses pixel-perfect system animation polish, accessibility integrations, and automatic OS updates.

2Picture-in-Picture: Private AVKit content source vs. public sample-buffer layer

Closed path: Native Picture-in-Picture is fully supported via public AVSampleBufferDisplayLayer APIs.

Picture-in-Picture (PiP) allows a user to shrink a video into a floating window that persists across apps and the Home Screen. Historically on iOS, PiP was strictly tied to Apple's AVPlayerLayer. Third-party video engines that generated their own frames or handled adaptive streaming out of process could not trigger system PiP without private APIs.

Starting with iOS 15, Apple introduced a public mechanism for custom video engines: AVPictureInPictureControllerContentSource initialized with an AVSampleBufferDisplayLayer and an AVPictureInPictureSampleBufferPlaybackDelegate. Through this API, an application provides decoded video sample buffers (CMSampleBuffer) and receives playback callbacks (play, pause, skip, seek) directly from the floating PiP window. WebKit itself continues to use an internal AVKit SPI path (connecting its synthetic WebAVPlayerController to a private content view controller), but the public path means alternative engines have a fully functional route to native Picture-in-Picture.

Public path available: Unlike fullscreen video playback, native Picture-in-Picture is not blocked for third-party browser engines. An engine that outputs decoded frames to an AVSampleBufferDisplayLayer can initialize AVPictureInPictureController using public iOS 15+ APIs and achieve full PiP functionality.

How Safari / WebKit does it

  • WebKit instantiates AVPictureInPictureContentViewController using its private WebAVPlayerController instance.
  • In VideoPresentationInterfaceAVKitLegacy.mm, WebKit calls the private SPI constructor -[AVPictureInPictureControllerContentSource initWithSourceView:contentViewController:playerController:] declared in AVPictureInPictureController_GenericSupport.h.
  • This tightly couples PiP transport commands to WebKit's internal playback session model and allows WebKit to synchronize playback state directly with AVKit's internal state machine.

What a BrowserEngineKit browser can do

  • Adopt the public AVPictureInPictureController.ContentSource(sampleBufferDisplayLayer:playbackDelegate:) API introduced in iOS 15.0.
  • Implement AVPictureInPictureSampleBufferPlaybackDelegate to handle play, pause, and time-skipping requests dispatched from the system PiP floating window.
  • While this requires the engine to manage sample buffer delivery and timing synchronization across process boundaries, it produces the exact same floating system PiP window with native gestures and controls.

3Lock Screen & Control Center "Now Playing": MediaRemote SPI vs. public MediaPlayer

When media is playing, iOS displays track metadata, album art, elapsed time, and playback controls in Control Center, on the Lock Screen, and in the Dynamic Island. The system daemon responsible for managing these controls is mediaremoted. Regular iOS apps interact with this daemon via the public MediaPlayer framework using MPNowPlayingInfoCenter and MPRemoteCommandCenter.

WebKit does not use MPNowPlayingInfoCenter. Instead, WebKit's media session management subsystem directly calls private MediaRemote.framework functions (prefixed with MRMediaRemote*) from within its isolated auxiliary processes (the WebContent process and the GPU process). This architecture relies on three private entitlements: com.apple.mediaremote.set-playback-state, com.apple.mediaremote.external-artwork-validation, and com.apple.mediaremote.ui-control. These entitlements allow WebKit's background processes to register playback state directly with mediaremoted, supply raw image data for album artwork, spoof the parent application bundle identifier via MRMediaRemoteSetParentApplication, and suppress system Now Playing activity presentation when appropriate.

How Safari / WebKit does it

  • In MediaSessionManagerCocoa.mm, WebKit calls MRMediaRemoteSetCanBeNowPlayingApplication(true) and constructs metadata dictionaries using private keys (kMRMediaRemoteNowPlayingInfoTitle, ArtworkData, etc.).
  • WebKit calls MRMediaRemoteSetParentApplication to attribute playback from helper processes back to Safari, and calls MRMediaRemoteSetNowPlayingApplicationPlaybackStateForOrigin to update state.
  • In RemoteCommandListenerCocoa.mm, WebKit registers command handlers using MRMediaRemoteSetSupportedCommands and MRMediaRemoteAddAsyncCommandHandlerBlock.
  • WebKit holds com.apple.mediaremote.set-playback-state, com.apple.mediaremote.external-artwork-validation, and com.apple.mediaremote.ui-control in its GPU and WebContent processes.

What a BrowserEngineKit browser can do

  • Third-party browsers cannot obtain com.apple.mediaremote.* entitlements and cannot invoke private MRMediaRemote SPIs; attempts to look up com.apple.mediaremoted.xpc from unentitled auxiliary processes will fail or be rejected.
  • Instead, third-party engines must manage Now Playing metadata in the main application process using public MPNowPlayingInfoCenter.default().nowPlayingInfo and MPRemoteCommandCenter.shared().
  • When web content or the rendering process updates media state (e.g. via the W3C Media Session API), the engine must serialize titles, artist info, duration, and artwork across internal IPC back to the host UI process to update the public center. Remote command events must likewise be forwarded back into the engine process.

4AirPlay routing: AVPlayer streaming constraints and public route picker

No capability gap: AirPlay route selection and video streaming operate under the exact same technical constraints for both Safari and third-party engines.

AirPlay allows an iOS device to send video or audio wirelessly to an Apple TV, HomePod, or AirPlay-compatible smart television. There is widespread confusion among web developers about whether Safari possesses exclusive AirPlay capabilities that third-party browser engines cannot access.

An inspection of WebKit source reveals that AirPlay video streaming is not an engine-exclusive gap. On iOS, WebKit's video streaming to AirPlay devices operates strictly through Apple's high-level AVPlayer (via MediaPlayerPrivateAVFoundationObjC.mm, which sets [m_avPlayer setAllowsExternalPlayback:YES]). WebKit's custom Media Source Extensions (MSE) pipeline (MediaPlayerPrivateMediaSourceAVFObjC.mm), which handles adaptive chunked streaming for web video, does not support AirPlay video playback at all. When a user taps AirPlay on an MSE-based video player in Safari, Safari cannot push the raw sample buffer stream over AirPlay; instead, it relies on the web application providing an alternate HLS manifest URL (or progressive MP4), switching playback to an AVPlayer pipeline.

No capability gap: AirPlay route selection and video streaming operate under the exact same technical constraints for both Safari and third-party engines. Both can present the public AVRoutePickerView, and both can stream video to AirPlay destinations only when the media is handed to an AVPlayer pointed at an HLS or progressive media URL.

How Safari / WebKit does it

  • In MediaPlayerPrivateAVFoundationObjC.mm, WebKit queries [m_avPlayer allowsExternalPlayback] and passes setAllowsExternalPlayback:!disabled.
  • For audio playback, WebKit routes system audio through the active AVAudioSession route configured by the system.
  • In MediaPlayerPrivateMediaSourceAVFObjC.mm, no wireless playback methods are implemented; WebKit cannot transmit custom MSE sample buffers over AirPlay without screen mirroring.

What a BrowserEngineKit browser can do

  • Display the system AirPlay route picker using the public AVRoutePickerView component from AVKit.
  • Stream video to AirPlay devices identically by instantiating an AVPlayer pointed to an HLS manifest or direct video URL whenever external playback is requested.
  • Route web audio through AirPlay endpoints automatically via standard public AVAudioSession category configurations (AVAudioSessionCategoryPlayback).

5Protected content (FairPlay DRM & EME): The sample-buffer attachment barrier

Commercial streaming services (such as Netflix, Apple TV+, and Disney+) protect premium video content using Encrypted Media Extensions (EME) coupled with a hardware-backed Digital Rights Management (DRM) system. On Apple platforms, the native DRM system is FairPlay Streaming (FPS). In standard web architectures, the web application requests decryption keys from a Key Server and attaches them to encrypted video samples before playback.

While Apple provides public APIs for FairPlay license acquisition through AVContentKeySession, a critical entitlement barrier prevents third-party browser engines from using FairPlay with custom media pipelines in auxiliary processes. In WebKit's implementation (CDMInstanceFairPlayStreamingAVFObjC.mm), the GPU process attaches decryption keys to encrypted video frames using AVSampleBufferAttachContentKey. That function is guarded inside CoreMedia by the private entitlement com.apple.private.coremedia.allow-fps-attachment. WebKit's own build scripts in process-entitlements.sh explicitly deny this entitlement to GPUExtension (the BrowserEngineKit auxiliary extension target). Consequently, a third-party browser engine running a separate GPU or rendering extension cannot decrypt FairPlay-protected sample buffers in its auxiliary pipeline.

How Safari / WebKit does it

  • WebKit signs its standard GPU process with com.apple.private.coremedia.allow-fps-attachment in process-entitlements.sh.
  • In CDMInstanceFairPlayStreamingAVFObjC.mm, WebKit invokes AVSampleBufferAttachContentKey directly on encrypted CMSampleBuffer objects in the GPU process.
  • WebKit also holds com.apple.developer.coremedia.allow-alternate-video-decoder-selection in both WebContent and GPU processes, allowing it to choose specialized hardware decoding paths in VideoToolbox.

What a BrowserEngineKit browser can do

  • Use the public AVContentKeySession class to negotiate FairPlay license requests and fetch content keys.
  • However, because com.apple.private.coremedia.allow-fps-attachment is an Apple-internal entitlement explicitly excluded from GPUExtension, the engine cannot attach content keys directly to custom sample buffers in an isolated GPU process.
  • To play FairPlay protected content on iOS, an alternative browser must delegate the entire playback stream to Apple's high-level AVPlayer / AVPlayerLayer, forfeiting custom MSE demuxers, custom codecs, and in-engine video processing for DRM media.

6The Media Capabilities API & adaptive streaming ladders

Modern streaming video platforms—including YouTube, Netflix, Disney+, Max, and Vimeo—do not serve a single monolithic video file. Instead, they produce an adaptive bitrate (ABR) ladder containing dozens of separate video streams encoded across multiple codecs (H.264, HEVC, VP9, AV1), resolutions (720p, 1080p, 4K, 8K), frame rates (24, 30, 60, 120 fps), bit depths (8-bit vs. 10-bit), and dynamic ranges (Standard Dynamic Range vs. HDR10 or Dolby Vision).

Before initiating playback or when selecting which representation to stream, the web application calls the W3C standard API navigator.mediaCapabilities.decodingInfo(configuration). The browser responds with a promise resolving to three crucial boolean signals:

  • supported: Whether the device has a decoder that can parse and decompress the stream at all.
  • smooth: Whether the device can decode and present the video frames at full frame rate in real time without dropping frames or causing visible stutter.
  • powerEfficient: Whether the video is decoded using dedicated low-power hardware silicon rather than CPU software emulation that drains battery and causes device heating.

If a browser reports smooth: false for 4K 60fps HEVC, the streaming player omits that tier from its ladder or starts the stream at 1080p. If it falsely reports smooth: true on hardware that cannot sustain the frame rate, the user suffers choppy playback and audio-video desync. The accuracy of this API is therefore central to high-resolution web video delivery.

Does the private decoder capability dictionary represent an across-the-board media gap for all video on iOS? A thorough audit of WebKit's source code reveals that it does not. WebKit itself only uses the private capability dictionaries for three specific formats: HEVC, Dolby Vision, and AV1. For legacy and open codecs, WebKit relies on public APIs and heuristics that third-party engines can replicate with complete parity.

7Decoder capability tables (HEVC, Dolby Vision, AV1) & MaxPlaybackLevel

High Efficiency Video Coding (HEVC / H.265) is Apple's primary hardware codec for 4K video, HDR10, and high-framerate media. Rather than performing trial decodes or maintaining static tables inside WebKit source code, Safari queries iOS's internal VideoToolbox decoder registry directly via VTCopyHEVCDecoderCapabilitiesDictionary().

This private function returns a comprehensive CoreFoundation dictionary describing the device's silicon capabilities. WebKit inspects top-level and per-profile keys:

  • kVTHEVCDecoderCapability_SupportedProfiles: An array of supported profile identifiers (such as Main or Main 10). WebKit confirms the requested generalProfileIDC is present.
  • kVTHEVCDecoderCapability_PerProfileSupport: A dictionary mapping each profile identifier string to its specific performance constraints.
  • kVTHEVCDecoderProfileCapability_IsHardwareAccelerated: A boolean flag indicating whether the profile is backed by dedicated hardware silicon. WebKit assigns this directly to info.powerEfficient.
  • kVTHEVCDecoderProfileCapability_MaxDecodeLevel: The maximum HEVC level the decoder can process (e.g., Level 5.1 or Level 6). If the requested level exceeds this value, WebKit rejects the configuration as unsupported (supported: false).
  • kVTHEVCDecoderProfileCapability_MaxPlaybackLevel: The highest level the decoder can play back smoothly in real time.

The determination of smooth is remarkably concise and deterministic in WebKit source:

if (RetainPtr cfMaxPlaybackLevel = dynamic_cf_cast<CFNumberRef>(CFDictionaryGetValue(profileSupport.get(), kVTHEVCDecoderProfileCapability_MaxPlaybackLevel))) {
    int16_t maxPlaybackLevel = 0;
    if (!CFNumberGetValue(cfMaxPlaybackLevel.get(), kCFNumberSInt16Type, &maxPlaybackLevel))
        return std::nullopt;

    info.smooth = parameters.generalLevelIDC <= maxPlaybackLevel;
}

This distinction between MaxDecodeLevel and MaxPlaybackLevel is critical: an older iPhone SoC may be capable of decoding an 8K or 4K@60fps HEVC stream offline or at reduced throughput, but its display and decoder pipeline can only guarantee smooth real-time rendering up to Level 5.0 (4K@30fps). Safari knows this exact boundary without guessing.

Dolby Vision is an advanced high-dynamic-range (HDR) format that combines a video bitstream (typically HEVC) with dynamic per-frame tone mapping metadata. Video services such as Apple TV+, Netflix, and Max query Dolby Vision support using four-character codec identifiers such as dvh1 or dvhe followed by profile and level indicators (e.g., dvh1.05.06 for Profile 5, Level 6).

Because Dolby Vision decoders on Apple devices are tightly integrated into the hardware display engine, support for specific profile IDs (such as Profile 5 for single-layer HDR or Profile 8 for cross-compatible HDR) is hardware- and firmware-dependent. Safari queries these parameters through the same HEVC capabilities dictionary.

In Source/WebCore/platform/graphics/cocoa/HEVCUtilitiesCocoa.mm (validateDoViParameters), WebKit extracts Dolby Vision specific capability keys from the dictionary returned by VTCopyHEVCDecoderCapabilitiesDictionary():

WebKit parses these arrays into integer vectors, validates that the requested bitstreamProfileID and bitstreamLevelID are contained within the system arrays, and confirms that the codec instance can be initialized via VTSelectAndCreateVideoDecoderInstance. If valid, WebKit returns supported: true, smooth: true, and powerEfficient: isHardwareAccelerated.

AOMedia Video 1 (AV1) is the royalty-free video standard increasingly preferred by YouTube, Netflix, and other major streaming providers for its superior compression efficiency over HEVC. Hardware AV1 decoding is relatively new to Apple hardware: it was first introduced in the Apple A17 Pro (iPhone 15 Pro) and the M3 family of chips. Older devices have no hardware AV1 decoder at all, and even on supported devices, decoder throughput depends heavily on resolution, chroma format, bit depth, and HDR tone mapping.

When web players query AV1 capabilities (codec strings starting with av01), WebKit invokes validateAV1Parameters() in Source/WebCore/platform/graphics/cocoa/AV1UtilitiesCocoa.mm. To understand why this capability gap persists, it is necessary to examine how Apple classifies these symbols in its software architecture and security model.

Both VTCopyHEVCDecoderCapabilitiesDictionary and VTCopyAV1DecoderCapabilitiesDictionary are in-process C functions exported dynamically by /System/Library/Frameworks/VideoToolbox.framework. In WebKit's source code, they are declared in Source/WebCore/platform/cocoa/VideoToolboxSoftLink.h (lines 69–72) via SOFT_LINK_FUNCTION_MAY_FAIL_FOR_HEADER and cataloged in WebKit's SPI allowlist at Source/WebCore/Configurations/AllowedSPI-legacy.toml (lines 723–724). They are not declared in public SDK headers.

Crucially, neither function is restricted by kernel sandbox Seatbelt profiles or process-level entitlements. WebKit calls them directly in the WebContent process or GPU process without presenting a specialized entitlement. The restriction on third-party browsers is purely an API access boundary enforced by the App Store submission scanner, which flags dynamic or link-time references to non-public Apple symbols.

When Apple designed BrowserEngineKit to enable alternative browser engines, it introduced entitlements and classes for JIT compilation, out-of-process networking, memory management, and process lifecycle. However, Apple did not provide any decoder capability inspection API in BrowserEngineKit or VideoToolbox. Consequently, a third-party engine running with full BrowserEngineKit entitlements has no sanctioned method to inspect iOS decoder capability tables.

How Safari / WebKit does it

  • In HEVCUtilitiesCocoa.mm (validateHEVCParameters), WebKit soft-links VTCopyHEVCDecoderCapabilitiesDictionary and its capability key constants from VideoToolbox.
  • It verifies profile presence, checks hardware acceleration for powerEfficient, verifies generalLevelIDC ≤ maxDecodeLevel for supported, and sets info.smooth = (generalLevelIDC ≤ maxPlaybackLevel).
  • The entire query runs synchronously in memory without instantiating a decoder session or allocating video buffers.
  • validateDoViParameters reuses VTCopyHEVCDecoderCapabilitiesDictionary() to fetch supported profile and level arrays.
  • It checks whether the requested stream profile is permitted for HDR playback (Profiles 4, 5, 7, and 8 on iOS), verifies both profile and level membership, and validates decoder creation.
  • Accurately informs web players whether high-profile Dolby Vision content will render correctly on the device display.
  • In AV1UtilitiesCocoa.mm, WebKit queries VTCopyAV1DecoderCapabilitiesDictionary() to inspect exact hardware limits for profiles, levels, chroma subsampling, and color depth.
  • Distinguishes between standard dynamic range smooth playback (MaxPlaybackLevel) and HDR smooth playback (MaxHDRPlaybackLevel), accounting for the extra processing load of HDR tone mapping.
  • WebKit soft-links the private VideoToolbox symbols dynamically. As a system component, it compiles and runs without App Store review constraints.
  • Automatically inherits any new decoder profile or level capability added by Apple in future iOS updates without changing WebKit application logic.

What a BrowserEngineKit browser can do

  • Cannot call VTCopyHEVCDecoderCapabilitiesDictionary. It is a private C symbol in VideoToolbox.framework that is rejected by App Store submission checks.
  • BrowserEngineKit provides no replacement capability API. The only public VideoToolbox query is VTIsHardwareDecodeSupported(kCMVideoCodecType_HEVC), which returns a single boolean and contains no profile, level, or framerate information.
  • To answer smooth, the engine must either hardcode a table of every Apple A-series and M-series chip's max playback levels, or guess based on screen resolution and frame rate heuristics.
  • No public iOS API exists to enumerate supported Dolby Vision profiles or levels for web media engines.
  • While high-level system playback via AVPlayer can handle Dolby Vision URLs, custom media pipelines in alternative browser engines (like WebCodecs or Media Source Extensions) cannot verify profile support without the private VideoToolbox dictionary.
  • Engines must either claim lack of Dolby Vision support (forcing fallback to HDR10 or SDR) or hardcode device profile lists.
  • A third-party engine cannot call VTCopyAV1DecoderCapabilitiesDictionary().
  • Public VideoToolbox only offers VTIsHardwareDecodeSupported('av01'). This function confirms whether an A17 Pro or M3+ chip has AV1 hardware decode, but says nothing about whether 4K@60fps HDR is smoothly playable versus 1080p SDR.
  • Without this dictionary, an engine must guess whether AV1 HDR at high levels will drop frames, risking poor playback on borderline resolutions.
  • Cannot link or dynamically load the private VideoToolbox symbols without violating App Store submission guidelines.
  • Has no public BrowserEngineKit API to query decoder capability dictionaries.
  • Must maintain and ship its own static lookup table of Apple SoC capabilities (mapping chip identifiers to max playback levels), updating the browser application whenever Apple releases new hardware.

8Background audio, process isolation & the BrowserEngineKit capability path

Public path available: BrowserEngineKit provides the exact same BEProcessCapability mediaPlaybackAndCapture API that WebKit itself uses when embedded, enabling full parity for ongoing playback and Voice calls.

When an iOS user plays music, a podcast, or a video on a web page and switches to another app or locks their device, they expect the audio track to keep playing continuously. On iOS, background apps are normally suspended by RunningBoard (the iOS system daemon responsible for process life-cycle and priority management) within approximately 30 seconds. To prevent the audio stream from freezing, the browser must hold active assertions that inform the operating system that audible media is currently playing.

In Safari, WebKit coordinates this across multiple processes. When any web page begins producing sound, WebKit increments an audible media counter. The main browser process (WebProcessPool) and the web content process (WebProcessProxy) take a dedicated process assertion of type ProcessAssertionType::MediaPlayback. WebKit translates this assertion directly to the RunningBoard assertion name MediaPlayback inside the private com.apple.webkit assertion domain. Acquiring assertions in this domain is restricted by the operating system: RunningBoard validates that the calling process holds the private Apple entitlement com.apple.runningboard.assertions.webkit.

Third-party browser engines cannot use private RunningBoard domains. Instead, BrowserEngineKit introduces a public capability system that allows a browser app to grant its helper extensions elevated execution states. For media playback and capture, the framework provides BEProcessCapability and BEMediaEnvironment.

Inspection of WebKit's own source code reveals a critical architectural division: WebKit does not translate MediaPlayback into a capability inside its generic assertion adapter (AssertionCapability.mm only translates Suspended, Background, and Foreground). When a third-party host runs WebKit with extension capabilities enabled (preferences.mediaCapabilityGrantsEnabled()), WebKit explicitly skips taking RunningBoard assertions. Instead, it activates a dedicated media subsystem built around MediaCapability and ExtensionCapabilityGranter.

Public path available: BrowserEngineKit provides the public method [BEProcessCapability mediaPlaybackAndCaptureWithEnvironment:]. WebKit itself uses this exact API to grant background execution rights to its WebContent and GPU processes when running inside a third-party host app, confirming that alternative engines can keep audio alive in the background without private RunningBoard entitlements.

Running audio and video playback across multi-process browser architectures requires careful coordination with iOS's aggressive process lifecycle manager (RunningBoard). If an auxiliary process decoding media is suspended by the operating system when the user switches tabs or locks the screen, playback immediately stutters or halts.

WebKit isolates all media decoding and audio rendering inside the sandboxed GPU process (com.apple.WebKit.GPU). To keep this process alive during background audio and video playback, WebKit takes RunningBoard assertions in the private com.apple.webkit assertion domain using the private entitlement com.apple.runningboard.assertions.webkit. WebKit also holds com.apple.private.mediaexperience.startrecordinginthebackground.allow and com.apple.private.mediaexperience.processassertionaudittokens.allow, which let its GPU process start recording in the background and pass client audit tokens into AVAudioSession so the system holds assertions on presenting app processes.

For third-party browser engines, BrowserEngineKit formalizes this through BEProcessCapability. By activating a mediaPlaybackAndCaptureWithEnvironment: capability grant on a rendering extension process, a third-party engine informs RunningBoard that the process is actively rendering audio or capturing media. This grants the extension necessary CPU execution time while media is playing.

On iOS, all audio output must be coordinated through an AVAudioSession. The operating system uses the active audio session to decide audio routing, ducking, interruptions, and whether an application in the background is authorized to keep running. However, in modern multi-process browser architectures, audio samples are decoded and rendered inside an auxiliary process (the GPU process or rendering extension), while the user and the system view the host browser app as the entity producing sound.

This creates an attribution dilemma: if an auxiliary process activates an audio session in the background, why doesn't iOS suspend the parent application? In first-party Safari, WebKit solves this with private SPI. Inside the GPU process, RemoteAudioSessionProxyManager collects the audit tokens of all "presenting applications" (such as Safari or apps embedding SFSafariViewController) and passes them to AudioSessionIOS::setPresentingProcesses(). That method calls the private SPI -[AVAudioSession setAuditTokensForProcessAssertion:error:], backed by the private entitlement com.apple.private.mediaexperience.processassertionaudittokens.allow. The audio daemon (mediaserverd) and MediaExperience then hold background assertions on the presenting application on the GPU process's behalf.

Playing audio in the background requires responding gracefully when other system events occur—such as an incoming cellular phone call, a Siri prompt, an alarm, or navigation spoken directions. When another audio session takes precedence, iOS generates an audio interruption notification (AVAudioSessionInterruptionNotification), and the browser must suspend playback and notify the web page.

In Safari, RemoteAudioSessionProxyManager::beginAudioSessionInterruption() receives interruptions from CoreAudio and relays them across IPC to all active proxies, pausing Web Audio contexts and HTML5 <audio> elements. For concurrent playback, WebKit evaluates categoryCanMixWithOthers() to determine whether ambient web sounds can mix with background music. For lock-screen and Control Center controls (Now Playing), Safari drives private MediaRemote.framework SPIs from within its auxiliary processes (detailed thoroughly on media-playback.html › Lock Screen & Control Center Now Playing). A BrowserEngineKit browser implements identical user-facing behavior using public Foundation and MediaPlayer APIs in its host process.

Because iOS background execution is heavily restricted, some web developers and application authors historically attempted to play "silent audio" (a silent looped audio track) to keep JavaScript execution, WebSockets, or background tasks alive after leaving the foreground. For a general-purpose web browser, this interacts directly with Apple App Store review policies and operating system power enforcement.

Apple's App Store Review Guideline 2.5.4 explicitly governs background execution modes: apps declaring UIBackgroundModes audio must only use that mode for audible playback intended for the user. A browser cannot simply keep its engine running indefinitely in the background under the guise of audio unless real media is playing. Furthermore, iOS audio daemons (mediaserverd) and battery monitoring systems track audio output power; playing digital silence or muted tracks while drawing CPU and network resources can result in system thermal throttling or background process termination by RunningBoard.

How Safari / WebKit does it

  • WebProcessPool::updateAudibleMediaAssertions() checks whether the host process holds com.apple.runningboard.assertions.webkit. If entitled, it takes a self-targeted MediaPlayback assertion on the UIProcess and an assertion on the GPU process.
  • WebProcessProxy::updateAudibleMediaAssertions() takes a corresponding MediaPlayback assertion on each WebContent process that hosts an audible web page.
  • ProcessAssertionCocoa.mm translates ProcessAssertionType::MediaPlayback to the literal string "MediaPlayback" under the domain "com.apple.webkit".
  • When audio stops, WebProcessPool starts a 5-second hysteresis timer (m_audibleActivityTimer) before releasing assertions, preventing rapid process suspension during track changes or brief pauses.
  • In standalone Safari, WebKit takes raw RunningBoard assertions directly, bypassing capability grants entirely.
  • When running inside an extension-based host application, WebProcessProxy::updateAudibleMediaAssertions() checks page->preferences().mediaCapabilityGrantsEnabled() and returns early, omitting the MediaPlayback RunningBoard assertion.
  • WebPageProxy::updateMediaCapability() creates a MediaCapability object representing the page's protocol, host, and port URL wrapped in a BEMediaEnvironment.
  • ExtensionCapabilityGranter calls [platformMediaEnvironment activateWithError:&error] and grants [BEProcessCapability mediaPlaybackAndCaptureWithEnvironment:environment] to both the WebContent extension process and the GPU rendering extension process.
  • WebKit signs its GPU process with com.apple.private.gpu-restricted and runs it under a specialized sandbox profile.
  • In ProcessAssertionCocoa.mm, WebKit translates media playback states into private RunningBoard assertions (MediaPlayback) within the com.apple.webkit domain.
  • In RemoteAudioSessionProxyManager.cpp, WebKit passes client audit tokens to -[AVAudioSession setAuditTokensForProcessAssertion:error:], backed by com.apple.private.mediaexperience.processassertionaudittokens.allow.
  • The GPU process is provisioned with com.apple.coreaudio.allow-vorbis-decode to decode Vorbis audio streams.
  • In RemoteAudioSessionProxyManager.cpp, the GPU process gathers the Mach audit tokens of the client application processes currently playing audio.
  • AudioSessionIOS::setPresentingProcesses() calls the private SPI -[AVAudioSession setAuditTokensForProcessAssertion:error:], declared in AVFoundationSPI.h under AVAudioSessionWebKitPrivate.
  • Apple signs the GPU process with com.apple.private.mediaexperience.processassertionaudittokens.allow and com.apple.tcc.delegated-services (with kTCCServiceCamera and kTCCServiceMicrophone), authorizing cross-process assertion delegation.
  • When mediaCapabilityGrantsEnabled is active, WebKit skips this SPI entirely (lines 184 and 274 of RemoteAudioSessionProxyManager.cpp).
  • RemoteAudioSessionProxyManager acts as an AudioSessionInterruptionObserver in the GPU process.
  • On interruption, it notifies RemoteAudioSessionProxy instances, which dispatch events to the WebContent process to pause HTML media elements and fire interruption events.
  • When the interruption ends with AVAudioSessionInterruptionOptionShouldResume, WebKit automatically resumes playback if the web page was playing when interrupted.
  • Now Playing metadata and remote transport commands (play, pause, next track) are routed directly from the GPU process using private MediaRemote SPI and entitlements (com.apple.mediaremote.set-playback-state).
  • Safari explicitly tracks whether media is audible. In WebProcessPool.cpp and WebProcessProxy.cpp, assertions are labeled "audible media" (hasAudibleWebPage).
  • If a video or audio track is muted (volume == 0 or muted == true), WebKit does not take the MediaPlayback RunningBoard assertion. Muted media pauses when backgrounded unless Picture-in-Picture is active.
  • First-party Safari is not subject to third-party App Store review, but its power management strictly conforms to the audible playback requirement to protect device battery life.

What a BrowserEngineKit browser can do

  • A third-party browser cannot acquire RunningBoard assertions in the com.apple.webkit domain because third-party binaries cannot obtain com.apple.runningboard.assertions.webkit.
  • Calling private RunningBoard APIs (RBSAssertion) directly without entitlements fails at runtime with an authorization error from the RunningBoard daemon.
  • Instead, third-party engines must use public process lifecycle capabilities provided by BrowserEngineKit (see aspect 2) and declare background audio capabilities at the application level.
  • The browser's host application must declare audio in its UIBackgroundModes array in Info.plist.
  • The host application instantiates a BEMediaEnvironment initialized with the active origin URL via -[BEMediaEnvironment initWithWebPageURL:].
  • The host obtains a capability grant via +[BEProcessCapability mediaPlaybackAndCaptureWithEnvironment:] and invokes grantCapability:error: on its rendering extension process (BERenderingProcess) and web content process (BEWebContentProcess).
  • As long as an audio stream is actively playing through an active AVAudioSession, the operating system permits the host app and both granted extension processes to continue executing while backgrounded or locked.
  • Host decoding inside a BrowserEngineKit rendering extension (com.apple.browser-engine.rendering).
  • Activate [BEProcessCapability mediaPlaybackAndCaptureWithEnvironment:env] while media is active to prevent RunningBoard from suspending the helper process in the background.
  • Configure audio sessions via public AVAudioSession in the main application with AVAudioSessionCategoryPlayback. The engine cannot hijack external presenting process assertions or use private MediaExperience tokens, but standalone browser applications do not need multi-client view service assertions.
  • Third-party browsers cannot call setAuditTokensForProcessAssertion:error: and cannot obtain com.apple.private.mediaexperience.processassertionaudittokens.allow.
  • Instead, the host browser application must activate its own AVAudioSession (typically category AVAudioSessionCategoryPlayback) in the main app process.
  • The host app pairs its audio session with the BrowserEngineKit BEMediaEnvironment, which binds the auxiliary rendering process's audio capture and playback to the host application's lifecycle.
  • If the engine renders audio via CoreAudio or AudioUnit within its rendering extension, the session remains anchored to the parent app's background audio entitlement.
  • The host application registers for public AVAudioSession.interruptionNotification and relays interruption begin and end events to its browser engine via internal IPC.
  • Audio ducking and mixing options are configured on the public AVAudioSession via setCategory(_:options:) (e.g. .duckOthers or .mixWithOthers).
  • Now Playing metadata is published from the host app process using public MPNowPlayingInfoCenter.default().nowPlayingInfo, and remote transport commands are received through MPRemoteCommandCenter.shared(), as documented on media-playback.html.
  • Third-party engines must mirror this constraint: background execution via mediaPlaybackAndCapture should only be maintained while the web page is producing audible sound.
  • Relying on silent audio to keep non-audio background web tasks (such as background file downloads or WebSocket synchronizations) alive risks App Store rejection under Guideline 2.5.4.
  • For legitimate background data transfers, engines should use dedicated background APIs such as BEDownloadMonitor (see background downloads) rather than keeping an audio session active.

9Microphone & Camera capture: Background initiation & origin attribution

When a web page accesses the user's camera or microphone (via WebRTC or navigator.mediaDevices.getUserMedia), iOS displays privacy indicators: an orange dot for microphone use and a green dot for camera use in the status bar and Dynamic Island. When the user opens Control Center, iOS displays an attribution pill identifying which application is capturing media.

In Safari, iOS goes one step further: Control Center specifically names the web page domain responsible for capture (for example, displaying "example.com in Safari"). WebKit accomplishes this by having its isolated GPU process publish attribution strings directly to systemstatusd using the private class STDynamicActivityAttributionPublisher. This mechanism is secured by private entitlements: com.apple.systemstatus.activityattribution (with wildcard identity assumption) and com.apple.private.mediaexperience.recordingWebsite.allow. Additionally, WebKit's GPU process adopts the parent application's TCC identity via tcc_identity_create using com.apple.tcc.delegated-services.

BrowserEngineKit includes a public class, BEMediaEnvironment, designed to associate a web page URL with media playback and capture capability grants. However, whether passing a BEMediaEnvironment to BEProcessCapability produces identical website attribution strings in Control Center without Apple's private SystemStatus daemon SPI remains unverified on hardware.

Web applications increasingly host real-time voice and video communications (such as WebRTC voice calls in Google Meet, Zoom Web, or Discord). When a user joins a voice call, locks their phone, and puts it in their pocket, they expect two things: their voice should continue transmitting without muting, and iOS should show a clear indicator that the microphone is active.

There is an important technical distinction between continuing microphone capture that was started in the foreground versus initiating microphone recording while already running in the background:

How Safari / WebKit does it

  • In GPUConnectionToWebProcessCocoa.mm, WebKit extracts the web origin and calls [STDynamicActivityAttributionPublisher setCurrentAttributionWebsiteString:auditToken:] or setCurrentAttributionStringWithFormat:auditToken: using format WEB_UI_NSSTRING(@"%@ in %%@").
  • In process-entitlements.sh, the GPU process is provisioned with com.apple.systemstatus.activityattribution, Mach lookup for the attribution service, and wildcard explicitly assumed identities.
  • The GPU process also holds com.apple.private.mediaexperience.recordingWebsite.allow, allowing MediaExperience to log origin-specific recording telemetry.
  • WebKit calls tcc_identity_create to attribute camera/mic privacy permissions back to the browser app bundle.
  • WebKit signs its GPU process with com.apple.private.mediaexperience.startrecordinginthebackground.allow (added in commit 2f0e3161c641) and com.apple.private.coremedia.extensions.audiorecording.allow.
  • This private entitlement permits mediaserverd and MediaExperience to activate audio capture sessions even when the application is not the active foreground process.
  • When audio capture transitions to the background, CoreAudioCaptureUnit::setIsInBackground(true) starts MediaCaptureStatusBarManager.
  • MediaCaptureStatusBarManager takes an SBSStatusBarStyleOverridesAssertion for UIStatusBarStyleOverrideWebRTCAudioCapture via private SpringBoardServices SPI (authorized by com.apple.springboard.statusbarstyleoverrides), providing a persistent system call banner that brings Safari back to the foreground when tapped.
  • Safari's GPU process holds com.apple.private.mediaexperience.recordingWebsite.allow, allowing iOS status indicators to name the specific website recording audio.

What a BrowserEngineKit browser can do

  • Third-party engines cannot use STDynamicActivityAttributionPublisher or com.apple.systemstatus.activityattribution, as these are private to Apple.
  • Under BrowserEngineKit, an engine creates a BEMediaEnvironment initialized with the page URL via [[BEMediaEnvironment alloc] initWithWebPageURL:url] and passes it to [BEProcessCapability mediaPlaybackAndCaptureWithEnvironment:environment].
  • This public capability grant keeps the rendering/capture extension runnable while recording. However, it is untested whether iOS displays the origin domain in Control Center or defaults to displaying only the parent application name.
  • Ongoing voice calls work: With UIBackgroundModes audio, AVAudioSessionCategoryPlayAndRecord, and the mediaPlaybackAndCapture capability, active microphone streaming continues uninterrupted when the browser is backgrounded or the screen is locked.
  • Background start is blocked: Third-party browser engines cannot obtain com.apple.private.mediaexperience.startrecordinginthebackground.allow. If a web application tries to start recording while in the background, mediaserverd rejects the audio unit initialization and the capture fails.
  • Status bar indicator: Third-party engines cannot call private SpringBoardServices SPI for UIStatusBarStyleOverrideWebRTCAudioCapture. Instead, iOS displays the standard system orange microphone dot or Dynamic Island indicator attributed to the host browser application.
  • Origin attribution: Without recordingWebsite.allow, the iOS privacy indicator attributes microphone use to the browser app itself rather than the specific web origin (see media-playback.html).

Open questions & confidence

  • Confidence: Medium. Public iOS media frameworks (AVKit, AVFoundation, MediaPlayer) are mature and fully documented, and WebKit's source code explicitly documents its private SPI workarounds. However, certain dynamic behaviors have not been measured on physical devices running alternative engines.
  • BEMediaEnvironment attribution on device: While WebKit adopts BEMediaEnvironment in MediaCapability.mm, we have not verified whether iOS Control Center renders the origin domain ("example.com in Chrome") for third-party engines without the private STDynamicActivityAttributionPublisher / com.apple.systemstatus.activityattribution daemon pathway.
  • FairPlay without allow-fps-attachment: It is verified from process-entitlements.sh:553 that GPUExtension is denied com.apple.private.coremedia.allow-fps-attachment. Whether an alternative engine could perform FairPlay decryption within its main host process using public AVContentKeySession and pass decrypted frames to its renderer requires device testing.
  • Custom fullscreen controls UX parity: Because third-party engines with custom decoders cannot use AVPlayerViewController, they must implement custom fullscreen controls. The gap here is polish, gesture handling (pinch-to-exit), and system accessibility rather than fundamental video display capability.
  • Site fallback behavior: It is unmeasured whether major streaming services (such as Netflix or YouTube) strictly abide by decodingInfo().smooth on iOS, or whether they maintain independent client-side device tiering maps based on navigator.userAgent or WebGL GPU renderer strings. If a site uses its own device tier list, the lack of API accuracy may not alter the served video resolution in practice.
  • Viability of static SoC tables: A third-party engine could theoretically replicate Apple's internal VideoToolbox tables by testing real devices once and packaging the resulting level mappings (e.g., A16 → HEVC Level 5.1 smooth; A17 Pro → AV1 Level 5.1 smooth) into the browser binary. While this eliminates the functional gap, it incurs ongoing maintenance debt with every new iPhone and iPad launch.
  • Trial decode performance overhead: Whether an engine could asynchronously benchmark short 1-second HEVC or AV1 clips at browser startup without noticeable battery or latency penalty remains untested.

Android comparison

On Android, media integration is fundamentally open and modular. Android does not restrict system fullscreen playback or Picture-in-Picture to a single proprietary player object:

  • Custom decoders and fullscreen: Android applications can render video into a standard SurfaceView or TextureView using any decoding pipeline (including Android's native MediaCodec API or third-party software decoders like FFmpeg or dav1d) and present fullscreen views using standard Android View hierarchies.
  • Picture-in-Picture: Any Android app can enter Picture-in-Picture mode by calling enterPictureInPictureMode(PictureInPictureParams); the system floats the entire Activity or Surface without requiring a specific system player component.
  • Protected Content (DRM): Android exposes MediaDrm and the Widevine Modular DRM plugin publicly to all applications. Alternative browser engines on Android (such as Chrome, Firefox, and Edge) use public MediaDrm APIs to decrypt protected sample buffers directly in their own media pipelines without Apple-style private signing entitlements.
  • Media Controls: Android's MediaSession and MediaSessionManager APIs are completely public, allowing any app or background service to publish metadata, playback state, and transport controls to the lock screen and notification shade.

Decoder Capabilities:

  • MediaCodecList: Publicly enumerates all hardware and software codecs registered on the device.
  • MediaCodecInfo.CodecCapabilities.profileLevels: A public array of CodecProfileLevel structs detailing every supported profile and level for every codec installed on the device.
  • MediaCodecInfo.VideoCapabilities: Public methods including isSizeSupported(width, height), getSupportedFrameRatesFor(width, height), and areSizeAndRateSupported(width, height, frameRate).
  • MediaCodecInfo.VideoCapabilities.PerformancePoint: Introduced in Android 10 (API 29), this public API explicitly allows applications to test whether a decoder can achieve real-time playback at a specific resolution and frame rate (e.g., 4K at 60 fps) without frame dropping.

Any browser engine on Android (Chromium, Gecko, or WebKit) can inspect these public tables to answer navigator.mediaCapabilities.decodingInfo() with complete fidelity. Alternative engines on Android do not need private APIs, device lookup tables, or trial decodes.

Background Audio & Calls:

  • Foreground services: Any Android browser can run a media playback or VoIP calling foreground service (Service.startForeground()) accompanied by a persistent notification. With foregroundServiceType="mediaPlayback" or "microphone", Android guarantees that the browser's audio processing threads and network connections remain fully active regardless of whether the screen is locked or another app is open.
  • MediaSession integration: Android's public MediaSession and MediaSessionCompat APIs allow any browser to publish playback metadata, lock-screen artwork, and receive hardware transport button commands identically to Chrome.
  • Background capture initiation: While modern Android versions (Android 11+) restrict background apps from starting microphone capture without foreground service grants, an application holding a running microphone foreground service can manage capture sessions according to standard Android permissions.
