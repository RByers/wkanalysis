1What a Home Screen web app is on iOS: WebClips and BEWebAppManifest

When a user adds a Progressive Web App (PWA) to their Home Screen in Safari, iOS does not simply save a bookmark shortcut that opens inside a browser tab. Instead, the operating system creates an isolated application instance with its own icon, title, display configuration, and full-screen window isolated from the main browser interface.

Under the hood, iOS implements Home Screen web apps as WebClips. WebClip bundles are stored on the local filesystem under ~/Library/WebClips/<UUID>.webclip, each containing an Info.plist with the web app's start URL (pageURL), title, orientation settings, and icons. When tapped on the Home Screen, iOS launches the web app under a dedicated host process—historically com.apple.webapp or com.apple.SafariViewService—which presents an app-like card in the iOS multitasking app switcher.

In iOS 17.5, Apple introduced a public class in BrowserEngineKit: BEWebAppManifest. When an alternative browser presents the standard iOS share sheet (using SFAddToHomeScreenActivityItem), it can pass an instance of BEWebAppManifest populated with the website's raw web app manifest JSON. This allows the system share sheet to extract the manifest's name, icons, and start URL to create a WebClip on the Home Screen. However, creating the WebClip is where BrowserEngineKit's integration ends: once installed, the third-party browser has no public way to interact with, manage, or launch that web app.

How Safari / WebKit does it

  • Safari passes website metadata and icons directly to UIKit's internal WebClip generation pipeline when the user taps "Add to Home Screen".
  • The resulting WebClip is registered with the system and executes within Safari's dedicated web-app host process (com.apple.SafariViewService), giving it standalone display mode, its own lifecycle, and its own task card in the iOS app switcher.
  • The WebClip's bundle identifier and origin are tracked by system daemons, enabling persistent push subscriptions, custom notification identities, and badge updates.

What a BrowserEngineKit browser can do

  • A third-party browser can instantiate BEWebAppManifest with initWithJSONData:manifestURL: (iOS 17.5+) and pass it to the share sheet's SFAddToHomeScreenActivityItem.
  • The system share sheet creates a WebClip on the user's Home Screen containing the website's metadata.
  • After installation, the third-party engine receives no callback, no WebClip identifier, and no handle to the installed web app. The browser cannot inspect or manage installed WebClips.

Evidence

  • AppleBEWebAppManifest — public BrowserEngineKit API (iOS 17.5+) representing a parsed web application manifest.
  • WebKitWebClipCache.mm:54–59 — demonstrates [UIWebClip pathForWebClipWithIdentifier:] resolving to the clip's Info.plist in the filesystem.
  • WebKitWebPushDaemon.mm:135–137 — references the native web app action bundle identifier com.apple.webapp for com.apple.SafariViewService.

2Enumerating and identifying installed web apps: UIWebClip SPI and sandbox boundaries

For a browser to support push subscriptions, badge counts, and notifications for a Home Screen web app, it must first be able to enumerate installed web apps and correlate an incoming web origin with its corresponding Home Screen icon. In Safari, this discovery is performed automatically in the background.

WebKit achieves this through UIWebClip, a private UIKit class. In WebKit's web push daemon (webpushd), the WebClipCache component calls [UIWebClip webClips] to obtain a complete list of all installed WebClips on the device. For each clip, it inspects pageURL to match against the website's security origin (WebCore::SecurityOriginData), inspects filesystem creation timestamps (FileSystem::fileCreationTime) to select the primary clip, and checks the private property trustedClientBundleIdentifiers.

Furthermore, reading installed WebClips requires direct access to ~/Library/WebClips. Standard iOS application containers are heavily sandboxed and strictly blocked from reading system or other applications' directories. WebKit's webpushd daemon has an explicit Seatbelt sandbox rule in com.apple.WebKit.webpushd.sb.in granting (allow file-read* (home-subpath "/Library/WebClips")). Third-party browser engines have neither the sandbox rule nor access to the private UIWebClip class.

How Safari / WebKit does it

  • WebClipCache::webClipIdentifierForOrigin calls [UIWebClip webClips] to scan all installed web apps and find one matching the requested origin URL.
  • WebKit checks trustedClientBundleIdentifiers on each WebClip to determine which application owns or has access to the clip.
  • The daemon carries an explicit sandbox exemption to read ~/Library/WebClips and caches preferred WebClip identifiers in a persistent property list (WebClipCache.plist).

What a BrowserEngineKit browser can do

  • Nothing equivalent. UIWebClip is private UIKit SPI (listed in WebKit's AllowedSPI.toml and UIKitSPI.h) that is completely off-limits to App Store applications.
  • A third-party browser's sandbox prevents reading ~/Library/WebClips, so the engine cannot read Info.plist files or inspect installed clips directly.
  • A third-party engine cannot discover whether the user has installed a specific website, cannot get its clip identifier, and cannot know if the user subsequently uninstalled or deleted the web app.

Evidence

  • WebKitWebClipCache.mm:68–98 — webClipIdentifierForOrigin uses [UIWebClip webClips], webClip.pageURL, and trustedClientBundleIdentifiers to identify matching installed web apps.
  • WebKitUIKitSPI.h:183–191 — private header declarations for UIWebClip methods: webClips, webClipWithIdentifier:, pathForWebClipWithIdentifier:, pageURL, and trustedClientBundleIdentifiers.
  • WebKitcom.apple.WebKit.webpushd.sb.in:188–190 — Seatbelt profile rule: (allow file-read* (home-subpath "/Library/WebClips")).
  • Commit77532e760a8b (2024-09-10) "Implicit web clip mode should choose a web clip that is visible to the application" — introduces WebClipCache and visibility filtering via trustedClientBundleIdentifiers.

3Per-web-app notification identity: synthetic PushBundle domains and private proxy entitlements

In Safari, when a Home Screen web app asks for notification permission and displays notifications, it behaves like an independent native application. The notification prompt displays the web app's own name and icon. When a notification arrives on the lock screen, it shows the web app's icon, the web app's title, and a subtitle attributing the source (e.g. "from Acme News"). In iOS Settings, the web app appears with its own individual entry under Notifications, allowing the user to configure alerts, sounds, and banners specifically for that web app without affecting Safari.

To achieve this, WebKit creates a synthetic bundle identity for every web app. In WebPushDaemon.mm, the helper function platformNotificationCenterBundleIdentifier formats a dedicated bundle ID: com.apple.WebKit.PushBundle.<webClipIdentifier>. WebKit then instantiates UNUserNotificationCenter using an Apple-private initializer: [[UNUserNotificationCenter alloc] initWithBundleIdentifier:notificationCenterBundleIdentifier]. It configures the notification's icon via private SPI [UNNotificationIcon iconForApplicationIdentifier:] and sets the default action bundle identifier to com.apple.webapp.

Normally, iOS's notification daemon (usernotificationsd) enforces that an application can only post notifications under its own code-signed bundle identifier. WebKit bypasses this restriction through an Apple-private entitlement granted to webpushd in process-entitlements.sh: com.apple.private.usernotifications.app-management-domain.proxy, set to the domain string com.apple.WebKit.PushBundles, alongside com.apple.usernotification.notificationschedulerproxy and Mach lookup access to com.apple.usernotifications.listener.

How Safari / WebKit does it

  • webpushd generates an isolated synthetic bundle identifier (com.apple.WebKit.PushBundle.<webClipIdentifier>) for each installed web app.
  • It uses the private constructor -[UNUserNotificationCenter initWithBundleIdentifier:] to create an isolated notification center for that synthetic bundle.
  • Backed by com.apple.private.usernotifications.app-management-domain.proxy, usernotificationsd grants the synthetic bundle its own permission record in iOS Settings and independent delivery controls.
  • Notifications display the web app's icon via [UNNotificationIcon iconForApplicationIdentifier:] and route taps directly to com.apple.webapp.

What a BrowserEngineKit browser can do

  • Third-party apps only have access to +[UNUserNotificationCenter currentNotificationCenter], which represents the browser app as a whole.
  • Calling private constructors like initWithBundleIdentifier: is rejected by the system without the private app-management-domain.proxy entitlement, which Apple does not grant to third parties.
  • All web-app notifications scheduled by a third-party engine appear with the browser's own name and icon, not the web app's.
  • All web apps share the single notification permission of the parent browser in iOS Settings: revoking permission mutes the entire browser and all installed web apps simultaneously.

Evidence

  • WebKitWebPushDaemon.mm:144–147 — platformNotificationCenterBundleIdentifier formats synthetic bundle IDs as com.apple.WebKit.PushBundle.%@.
  • WebKitWebPushDaemon.mm:1018–1055 — showNotification sets defaultActionBundleIdentifier to com.apple.webapp, sets content.icon = [UNNotificationIcon iconForApplicationIdentifier:...], formats subtitle from <webClip title>, and schedules via [[UNUserNotificationCenter alloc] initWithBundleIdentifier:...].
  • WebKitUserNotificationsSPI.h:54–74 — private SPI declarations for UNNotificationIcon, UNMutableNotificationContent.icon, UNMutableNotificationContent.defaultActionBundleIdentifier, and -[UNUserNotificationCenter initWithBundleIdentifier:].
  • WebKitprocess-entitlements.sh:617 — grants com.apple.private.usernotifications.app-management-domain.proxy with value com.apple.WebKit.PushBundles to webpushd.

4Badging the web app icon: UISApplicationState vs. browser-level badging

The standard Web Badging API (navigator.setAppBadge() and navigator.clearAppBadge()) allows installed web applications to display a numeric badge on their Home Screen icon—for example, to indicate unread messages or pending notifications. In Safari, calling this API updates the badge number specifically on the Home Screen icon of the active web app.

In WebKit, when JavaScript executes navigator.setAppBadge(count), the call is forwarded across IPC from the rendering process to the Network Process and finally to webpushd. In WebPushDaemon.mm, the daemon uses UISApplicationState, a private class from Apple's UIKitServices framework:

RetainPtr state = adoptNS([[UISApplicationState alloc] initWithBundleIdentifier:platformNotificationCenterBundleIdentifier(identifier.pushPartition).get()]);
state.get().badgeValue = appBadge ? [NSNumber numberWithUnsignedLongLong:*appBadge] : nil;

This allows webpushd to target the Home Screen WebClip's synthetic bundle ID directly. Interacting with the system badging service requires Mach lookup access to com.apple.frontboard.systemappservices and the private entitlement com.apple.uikitservices.app.value-access (added to webpushd in August 2024 via commit 4433278ba6e8). Third-party applications have no access to UISApplicationState or frontboard.systemappservices.

How Safari / WebKit does it

  • NetworkNotificationManager::setAppBadge dispatches an IPC message to webpushd containing the target origin and requested badge count.
  • WebPushDaemon::setAppBadge allocates UISApplicationState initialized with the WebClip's synthetic bundle ID (com.apple.WebKit.PushBundle.<webClipIdentifier>) and sets badgeValue.
  • The system immediately updates the badge number on that specific WebClip icon on the user's Home Screen.

What a BrowserEngineKit browser can do

  • A third-party browser can only call public badge APIs: [UNUserNotificationCenter setBadgeCount:withCompletionHandler:] or UIApplication.applicationIconBadgeNumber.
  • These public APIs can only badge the browser application's own icon on the Home Screen.
  • There is no public API to badge a WebClip. If a web app installed via a third-party engine calls setAppBadge(5), the browser can either ignore it or put a "5" badge on the main browser's icon, confusing the user.

Evidence

  • WebKitWebPushDaemon.mm:1238–1241 — WebPushDaemon::setAppBadge allocates UISApplicationState with the synthetic bundle ID and assigns badgeValue.
  • WebKitUIKitSPI.h:110 — imports private header <UIKitServices/UISApplicationState.h>.

5Waking and launching the web app on push: FrontBoard SPI and sensitive URLs

When an incoming push notification arrives from the network while a Home Screen web app is not running, the web app's service worker needs to be activated in the background to handle the push event (for example, to decrypt the payload, fetch updated data, and show a notification). Furthermore, when the user taps on a notification, iOS must open the specific web application window rather than a generic browser tab.

In WebKit, webpushd receives incoming push events directly from Apple Push Notification service (apsd). To wake or launch the web-app host process in the background, WebPushDaemon.mm uses private application-launching mechanisms:

  • For Safari's web-app host (com.apple.SafariViewService), it synthesizes a custom URL with prefix webapp://web-push/<pushPartition> and invokes -[LSApplicationWorkspace openURL:configuration:completionHandler:] using a private _LSOpenConfiguration. It flags the configuration as sensitive = YES (authorized by the private entitlement com.apple.springboard.opensensitiveurl), sets FBSActivateForEventOptionTypeBackgroundContentFetching, and specifies the source application as com.apple.WebKit.webpushd (authorized by com.apple.private.launchservices.canspecifysourceapplication).
  • For other client processes, it utilizes SpringBoardServices SPI: SBSCreateOpenApplicationService() and calls -[SBSOpenApplicationService openApplication:withOptions:completion:], passing a FrontBoard BSAction payload configured with FBSOpenApplicationOptionKeyActivateSuspended: @YES and background content fetching. This requires the private entitlement com.apple.frontboard.launchapplications and the Seatbelt rule (allow lsopen).

How Safari / WebKit does it

  • webpushd listens to apsd in the background even when Safari and all web apps are closed.
  • Upon receiving a push payload, webpushd uses FrontBoard and LaunchServices SPIs to launch the web-app host process in the background with suspended activation.
  • The web-app host wakes up, executes the service worker's push event handler, and presents or updates the notification without foregrounding any user interface.

What a BrowserEngineKit browser can do

  • Third-party iOS applications cannot wake or launch secondary processes in the background. Public APIs like UIApplication.openURL: require explicit user interaction and cannot open sensitive system URL schemes.
  • Third-party apps cannot access SBSCreateOpenApplicationService or dispatch BSAction payloads via FrontBoard without com.apple.frontboard.launchapplications.
  • A third-party browser can only receive push notifications sent directly to the browser's own bundle identifier. Standard iOS background push processing is subject to aggressive system throttling (PowerLog and Duet Activity Scheduler), cannot guarantee prompt wake, and cannot launch an isolated web-app window.

Evidence

  • WebKitWebPushDaemon.mm:646–678 — launches client apps via SBSCreateOpenApplicationService, FBSOpenApplicationOptions, and BSAction with suspended background activation.
  • WebKitprocess-entitlements.sh:613–618 — signs webpushd with com.apple.springboard.opensensitiveurl, com.apple.private.launchservices.canspecifysourceapplication, and com.apple.frontboard.launchapplications.
  • WebKitcom.apple.WebKit.webpushd.sb.in:215 — Seatbelt profile rule: (allow lsopen).

6Why alternative engines cannot connect to webpushd: the private webpush entitlement and single-host lock-in

Given that Apple already developed a robust system daemon (webpushd) that handles WebClips, badges, push routing, and notification isolation on iOS, a natural question is: why can't a BrowserEngineKit browser simply connect to webpushd over XPC and let the system daemon manage its Home Screen web apps?

Reading WebKit's daemon source code reveals that webpushd is protected by two distinct enforcement layers that strictly lock out all non-Safari processes:

  1. Entitlement verification on connection: When an XPC client attempts to connect to webpushd, PushClientConnection::create inspects the client process's audit token. In PushClientConnection.mm, it verifies that the client holds the Apple-private entitlement com.apple.private.webkit.webpush: 
    if (!hostAppHasWebPushEntitlement) {
    RELEASE_LOG_ERROR(Push, "PushClientConnection::create failed: client is missing Web Push entitlement");
    return nullptr;
}
    This entitlement is not among the capabilities granted to BrowserEngineKit engines and cannot be obtained by third-party developers.
  2. Hardcoded single-host bundle check: Even if a client could pass the entitlement check, webpushd hardcodes an explicit restriction to a single host application. In WebPushDaemon.mm, the helper getAllowedBundleIdentifier() returns "com.apple.SafariViewService"_s. Both the incoming connection handler (connectionEventHandler, line 355) and the incoming push handler (handleIncomingPush, line 518) explicitly check: 
    if (getAllowedBundleIdentifier() != bundleIdentifier || ...) {
    RELEASE_LOG_ERROR(Push, "Got message from unexpected bundleIdentifier = %{public}s", bundleIdentifier.utf8());
    tryCloseRequestConnection(request);
    return;
}
    In commit 77532e760a8b, Apple engineers noted: "the design from the beginning was to only allow one app to access it [webpushd], so I changed methods that checked whether apps were allowed to connect to webpushd to only allow a single app to connect."

How Safari / WebKit does it

  • Safari and its web-app host (com.apple.SafariViewService) carry Apple's private entitlement com.apple.private.webkit.webpush.
  • webpushd specifically matches com.apple.SafariViewService as its allowed bundle identifier, establishing a trusted high-privilege IPC channel.
  • All push notifications, subscription persistence, and WebClip associations are serviced by the shared daemon.

What a BrowserEngineKit browser can do

  • Third-party browsers cannot obtain com.apple.private.webkit.webpush, causing PushClientConnection::create to immediately terminate any connection attempt.
  • Even if granted connection access, the daemon's internal logic strictly rejects any bundle identifier other than com.apple.SafariViewService.
  • A third-party browser is completely barred from using webpushd, forcing it to reinvent push notifications using standard public APIs that lack WebClip integration.

Evidence

  • WebKitPushClientConnection.mm:73 and :187–190 — defines hostAppWebPushEntitlement = "com.apple.private.webkit.webpush"_s and drops connections from clients missing it.
  • WebKitWebPushDaemon.mm:95–100 — getAllowedBundleIdentifier() hardcodes "com.apple.SafariViewService"_s.
  • WebKitWebPushDaemon.mm:355–360 and :518–522 — rejects messages and push delivery whenever the client bundle identifier does not match getAllowedBundleIdentifier().
  • Commit77532e760a8b (2024-09-10) — explicitly restricts webpushd to a single client application.

Android comparison

On Android, Progressive Web Apps installed to the home screen can be minted as WebAPKs (via Google Play Services or platform package management). A WebAPK is a real Android application package generated specifically for that web application, complete with its own unique package name (e.g. org.chromium.webapk.a...), distinct icon, and standalone entry in Android's system Settings.

Because a WebAPK has a first-class application identity on Android:

  • Notifications appear under the web app's own name and icon in the Android notification shade and status bar.
  • Notification channels and permissions are managed per web app in system Settings; muting an installed PWA does not mute the browser.
  • The web app can update the notification badge directly on its own launcher icon.
  • Background push notifications arrive via Firebase Cloud Messaging (FCM) and can wake the web app's background service worker directly.

Alternative browser engines on Android (such as Firefox or Samsung Internet) can either integrate with the platform's WebAPK minting service or install standalone shortcuts with dedicated notification channels. On iOS, by contrast, only Safari has access to the privileged system daemon and private entitlements necessary to simulate first-class application identity for web apps.
