1iCloud Private Relay & Apple privacy proxies

Apple’s iCloud Private Relay provides dual-hop encrypted proxying for iCloud+ subscribers, hiding a user’s IP address, DNS queries, and precise browsing location from both network operators and destination websites. In Safari, Private Relay activates automatically for all web browsing sessions. However, for a BrowserEngineKit browser running its own network stack, this protection silently disappears: web traffic travels directly over the open internet without passing through Private Relay.

Technically, WebKit’s Networking process configures Private Relay routing via private properties on NSMutableURLRequest in CFNetwork (Apple’s core networking framework). WebKit sets flags such as _privacyProxyFailClosed, _setPrivacyProxyFailClosedForUnreachableNonMainHosts:, and _setPrivacyProxyStrictFailClosed:, and checks _setProhibitPrivacyProxy: when relaying should be skipped. At the transport layer, CFNetwork cooperates with com.apple.networkserviceproxy (the system daemon that coordinates Apple and partner egress relays) and marks BSD sockets with internal kernel tags such as SO_MARK_KNOWN_TRACKER and SO_MARK_KNOWN_TRACKER_NON_APP_INITIATED. Third-party apps using standard NSURLSession only receive Private Relay coverage for unencrypted HTTP traffic and DNS; Apple does not route third-party HTTPS traffic through Private Relay. Furthermore, because alternative engines open raw BSD sockets directly or use public Network.framework primitives, their custom TLS/QUIC connections cannot invoke networkserviceproxy or opt into Private Relay.

How Safari / WebKit does it

  • NetworkDataTaskCocoa::NetworkDataTaskCocoa inspects navigation state and sets _setPrivacyProxyFailClosedForUnreachableNonMainHosts:YES, _setPrivacyProxyStrictFailClosed:YES, or _setPrivacyProxyFailClosed:YES on mutable requests.
  • WebKit’s iOS Networking sandbox allows Mach lookup to com.apple.networkserviceproxy.fetch-token and authorizes socket option names SO_MARK_KNOWN_TRACKER and SO_MARK_KNOWN_TRACKER_NON_APP_INITIATED to steer traffic through Apple’s relay infrastructure.
  • In Private Browsing, advanced privacy protections leverage CFNetwork’s strict fail-closed modes to guarantee that traffic never leaks over unproxied connections if the relay is temporarily unreachable.

What a BrowserEngineKit browser can do

  • No public path. Apple does not expose any API or entitlement for third-party sockets or network stacks to route through iCloud Private Relay.
  • Third-party engines opening TCP/UDP sockets directly connect to destination web servers without relay hops. Users who pay for iCloud+ and enable Private Relay in iOS Settings will not have their IP masked when browsing with Chrome or Firefox on iOS.
  • If an engine were to fall back to system NSURLSession, Apple’s documented policy still limits third-party app relaying strictly to insecure HTTP and DNS traffic, excluding general HTTPS web browsing.

2Oblivious HTTP (CipherML) & relay-backed services

Modern browser privacy features increasingly rely on Oblivious HTTP (OHTTP) to decouple a client's IP address from sensitive queries, such as Private Click Measurement (PCM) ad conversion attribution, privacy-preserving machine learning, and Safe Browsing URL hash checks. Safari routes these requests through Apple’s system-level privacy gateways without building bespoke relay infrastructure.

WebKit accomplishes this via two private Apple components. First, WebKit's Networking process and auxiliary attribution daemon (adattributiond) carry the private entitlement com.apple.private.ciphermld.allow, which permits Mach communication with com.apple.ciphermld—Apple's system daemon for CipherML and Oblivious HTTP operations. Second, adattributiond is granted com.apple.private.networkserviceproxy and an explicit Mach lookup exception for com.apple.networkserviceproxy (introduced in commit f8277ab0a96d to support proxying PCM requests on iOS). A BrowserEngineKit networking extension receives neither entitlement and is sandboxed away from both daemons.

How Safari / WebKit does it

  • process-entitlements.sh signs the Networking process with com.apple.private.ciphermld.allow (added in bdbf8bd332f6) and gives adattributiond the com.apple.private.networkserviceproxy entitlement.
  • The Networking sandbox grants Mach lookup access to com.apple.ciphermld, allowing WebKit to dispatch cryptographic OHTTP payloads directly through Apple’s gateway infrastructure.
  • PCM requests in adattributiond configure fail-closed privacy proxy routing via _privacyProxyFailClosed = YES.

What a BrowserEngineKit browser can do

  • Cannot access Apple’s OHTTP daemons. Both com.apple.ciphermld and com.apple.networkserviceproxy require private Apple entitlements and are blocked by the Seatbelt sandbox.
  • Engines must build and run their own external OHTTP infrastructure. For example, if Chromium implements Safe Browsing v5 hash prefixes or Privacy Sandbox conversion measurement via OHTTP on iOS, it must operate its own independent relay proxies, manage public keys, and bear the associated server infrastructure costs.

3Enterprise SSO, Kerberos & AppSSO handoffs

In enterprise deployments (corporations, universities, government fleets), users access internal web portals protected by Kerberos, NTLM, or modern identity providers (such as Microsoft Entra ID or Okta). Safari integrates natively with iOS's enterprise Single Sign-On (AppSSO) framework and Kerberos ticket management, allowing users to authenticate seamlessly without repeatedly entering usernames and passwords.

Inside WebKit, this is coordinated by a dedicated subsystem: SOAuthorizationCoordinator. When navigating to an enterprise domain, WebKit checks whether the URL can be handled by AppSSO using canPerformAuthorizationWithURL:callerBundleIdentifier:useInternalExtensions:YES. It explicitly calls [NSURLSession _disableAppSSO] to take direct ownership of the negotiation flow, intercepts HTTP 401 challenges, and communicates with com.apple.AppSSO.service-xpc and the system Kerberos ticket cache daemon (com.apple.GSSCred). In contrast, an engine running an independent network stack does not automatically trigger AppSSO extension flows or inherit GSS-API credentials.

How Safari / WebKit does it

  • SOAuthorizationCoordinator handles navigation actions, creating NavigationSOAuthorizationSession or RedirectSOAuthorizationSession delegates.
  • Uses private SPI selector canPerformAuthorizationWithURL:...useInternalExtensions:YES to query enterprise SSO extensions configured via MDM profiles.
  • The Networking sandbox profile allows Mach lookup to com.apple.AppSSO.service-xpc, com.apple.GSSCred (GSS-API Kerberos credentials), and com.apple.cfnetwork.AuthBrokerAgent.
  • WebKit’s Networking process holds com.apple.private.accounts.bundleidspoofing, allowing account verification queries to accountsd on behalf of client bundle identities.

What a BrowserEngineKit browser can do

  • Automatic OS SSO does not occur. A custom socket stack (such as Chromium’s HttpAuthHandlerNegotiate) cannot directly interact with com.apple.GSSCred or receive automatic AppSSO handoffs on raw HTTP 401 responses.
  • An engine can theoretically invoke Apple’s public AuthenticationServices API (ASAuthorizationSingleSignOnProvider), but this requires bridging in-flight network requests across process boundaries: halting socket read loops in the networking extension, dispatching an auth request to the UI process, presenting credentials, and replaying the HTTP transaction.
  • Neither Chromium nor Gecko implements this complex bridge on iOS today, resulting in enterprise users experiencing authentication prompts or broken intranet access.

Evidence

  • WebKitSOAuthorizationCoordinator.mm:59–85 — initializes AppSSO delegate, calls [NSURLSession _disableAppSSO], and queries canPerformAuthorizationWithURL:...useInternalExtensions:YES.
  • WebKitnetworking-defines.sb:102–103 — allows Mach lookup for com.apple.AppSSO.service-xpc.
  • WebKitnetworking-defines.sb:136 — allows Mach lookup for com.apple.GSSCred (Kerberos GSS-API).
  • WebKitprocess-entitlements.sh:636 — grants com.apple.private.accounts.bundleidspoofing to the Networking process.
  • AppleASAuthorizationSingleSignOnProvider — public Apple documentation for enterprise single sign-on.

4Enterprise proxies, PAC/WPAD & Per-App VPN

Enterprise Wi-Fi networks frequently mandate Proxy Auto-Configuration (PAC) scripts, Web Proxy Auto-Discovery (WPAD), or Per-App VPN tunnels to access internal resources. In Safari, CFNetwork transparently manages proxy scripts, evaluates JavaScript PAC rules via system daemons, and steers traffic through designated VPN tunnels without browser application intervention.

For alternative engines, handling enterprise proxy configurations presents architectural hurdles. While an engine can query system proxy dictionaries via the public C function CFNetworkCopySystemProxySettings(), evaluating a PAC file requires executing JavaScript inside the engine’s networking process. However, BrowserEngineKit’s networking extension sandbox strictly prohibits JIT compilation (JIT is restricted to rendering extensions with com.apple.developer.web-browser-engine.rendering), forcing PAC evaluation into slow interpreted mode or requiring out-of-process delegation. Furthermore, for enterprise Per-App VPNs, MDM profiles associate VPN tunnels with specific application bundle identifiers; because third-party networking code executes within an extension bundle (e.g., com.google.chrome.ios.NetworkingExtension), MDM profiles configured only for the main browser app may fail to route the extension's network sockets through the VPN tunnel.

How Safari / WebKit does it

  • CFNetwork automatically handles PAC fetching, execution, and WPAD via system helper daemons (com.apple.cfnetwork.AuthBrokerAgent and com.apple.cfnetwork.cfnetworkagent).
  • WebKit’s Networking process delegates its sockets to the host application’s identity using SO_DELEGATED, guaranteeing that Per-App VPN routing rules bound to the browser app apply directly to the network connection.
  • Sandboxed access to com.apple.nehelper and com.apple.nesessionmanager coordinates on-demand VPN tunnel activation.

What a BrowserEngineKit browser can do

  • Engines read static proxy IP/port configurations via CFNetworkCopySystemProxySettings(), which works reliably for standard HTTP/HTTPS/SOCKS proxies.
  • PAC execution requires the engine to bring its own JavaScript PAC runner without JIT acceleration, or manually invoke CFNetworkExecuteProxyAutoConfigurationURL.
  • Because third-party networking extensions cannot set SO_DELEGATED (see aspect 5), Per-App VPN tunnels configured in enterprise MDM profiles must explicitly include both the host app bundle ID and the networking extension bundle ID; otherwise, enterprise intranet requests leak outside the VPN tunnel.

Evidence

  • WebKitDNSResolveQueueCFNet.mm:59–74 — reads system proxy configuration via CFNetworkCopySystemProxySettings() and CFNetworkCopyProxiesForURL().
  • WebKitnetworking-defines.sb:62–64 and :142–144 — allows Mach lookup for NetworkExtension daemons com.apple.nesessionmanager and com.apple.nehelper.
  • WebKitnetworking-defines.sb:124–129 — allows Mach lookup for com.apple.cfnetwork.AuthBrokerAgent and com.apple.cfnetwork.cfnetworkagent.
  • AppleCFNetworkCopySystemProxySettings — public CFNetwork documentation.

5Low-level socket delegation & system attribution (SO_DELEGATED)

On iOS, the operating system tracks network bandwidth, cellular data limits, and battery consumption on a per-application basis, surfaced directly to users in "Settings › Cellular". When an app hosts WebKit, Safari or the host app receives the data and power attribution for page downloads rather than an obscure system helper process. WebKit achieves this through low-level kernel socket delegation.

Inside the Darwin kernel (XNU), delegating a BSD socket to another process audit token or PID requires the kernel privilege PRIV_NET_PRIVILEGED_SOCKET_DELEGATE. In WebKit, Apple’s signing script grants the Networking process the private entitlement com.apple.private.network.socket-delegate. WebKit’s Seatbelt sandbox profile specifically gates socket delegation on holding this entitlement: (allow system-privilege (with grant) (require-all (privilege-id PRIV_NET_PRIVILEGED_SOCKET_DELEGATE) (require-entitlement "com.apple.private.network.socket-delegate"))), enabling WebKit to call setsockopt with SO_DELEGATED. A third-party BrowserEngineKit networking extension receives only com.apple.developer.web-browser-engine.networking and cannot obtain the socket-delegation entitlement, meaning all data transfer and battery consumption are charged directly to the extension rather than delegated to the parent browser.

How Safari / WebKit does it

  • process-entitlements.sh injects com.apple.private.network.socket-delegate into the iOS Networking process.
  • Seatbelt grants system privilege PRIV_NET_PRIVILEGED_SOCKET_DELEGATE, allowing the process to set socket option SO_DELEGATED on BSD sockets.
  • Cellular data usage, radio wakeups, and battery attribution are accurately billed to the embedding application or Safari tab owner.

What a BrowserEngineKit browser can do

  • Third-party extensions cannot delegate sockets. com.apple.private.network.socket-delegate is an Apple-only entitlement not included in BrowserEngineKit.
  • Kernel calls to setsockopt(..., SO_DELEGATED, ...) fail with EPERM.
  • All network bytes and radio activity are logged under the extension process, confusing users checking cellular data menus in iOS Settings and potentially bypassing per-app cellular toggle restrictions.

6The custom-stack reality: what is irrelevant vs. what truly bites

Analysis of WebKit's source code identifies more than 230 private SPI symbols in CFNetwork and Network.framework used by WebKit’s Networking process. These cover HTTP/3 connection coalescing, connection pool fast lanes (_CFNetworkHTTPConnectionCacheSetLimit), custom protocol schemes, cookie partitioning (_setAllowOnlyPartitionedCookies:), and unified HTTP loaders (nw_settings_get_unified_http_enabled_webkit). For WebKit, these SPIs represent deep technical debt and platform entanglement.

However, for third-party browser engines, the vast majority of these private SPIs are completely irrelevant. Production browser engines—Chromium (with Cronet, BoringSSL, and QUICHE) and Gecko (with Necko and NSS)—bring their own complete, battle-tested transport stacks written in user space. They implement their own connection pooling, HTTP/2 multiplexing, HTTP/3/QUIC protocols, TLS handshake validation, and cookie jars directly over standard BSD UDP and TCP sockets. They do not use Apple’s CFNetwork session objects or Network.framework HTTP loaders.

The real boundary: The capability gap between Safari and third-party engines is not about HTTP/3 or WebTransport protocol implementations—it is strictly about operating system boundary services that require daemon cooperation or kernel privileges:
  • iCloud Private Relay: Hard capability gap. Third-party sockets cannot route through Apple's privacy relays.
  • Enterprise AppSSO: Polish and deployment gap. Seamless Kerberos and MDM single sign-on requires complex manual bridges rather than automatic OS interception.
  • Per-App VPN & PAC: Integration gap. JIT restrictions prevent fast in-process PAC evaluation, and lack of socket delegation complicates MDM VPN profile matching.
  • Socket Delegation: Accounting gap. Cellular data and power accounting cannot be delegated back to the parent app.

Android comparison

On Android, alternative browser engines also bring their own network stacks (Chromium/Cronet, Gecko/Necko). However, Android’s OS architecture handles network boundary services without giving first-party browsers structural privileges:

  • No exclusionary system proxy: Android does not operate a proprietary, first-party-only proxy equivalent to iCloud Private Relay. System VPNs and private DNS (DoT) apply uniformly across all apps at the OS level.
  • UID-based accounting: Android assigns a unique Linux User ID (UID) to each installed app package. All helper processes and threads spawned by the browser share the same UID, ensuring that cellular data limits, battery usage, and network activity are automatically attributed to the browser without requiring privileged kernel socket delegation.
  • Enterprise VPN routing: Android’s VpnService routes network traffic by UID. An enterprise per-app VPN configured via Android Enterprise Work Profiles automatically encompasses all sockets opened by the browser app and its subprocesses.
  • System proxy discovery: Android provides standard public APIs (ConnectivityManager.getDefaultProxy()) that expose host, port, and PAC URLs directly to apps, enabling custom network stacks to easily mirror system proxy settings.
