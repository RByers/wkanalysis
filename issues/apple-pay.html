1The multi-process payment pipeline and remote presentation

When a web user taps an "Apple Pay" button or initiates a purchase through the standard W3C Payment Request API, Safari immediately slides up a system payment sheet over the current web page. The user confirms the total, selects a shipping address and card, and authorizes the transaction using Face ID or Touch ID. Crucially, the sheet identifies the website as the merchant, not the browser application.

Under the hood on iOS, WebKit isolates this flow across its auxiliary processes. When page script invokes ApplePaySession or PaymentRequest, WebCore handles the state in PaymentCoordinator. Under the build flag ENABLE(APPLE_PAY_REMOTE_UI) (enabled on iOS and visionOS), WebKit does not handle payment presentation inside the main application process (the "UIProcess"). Instead, WebPaymentCoordinator dispatches IPC messages directly across processes to the Networking process. Inside the Networking process, NetworkConnectionToWebProcess instantiates a WebPaymentCoordinatorProxy and creates a PaymentAuthorizationController.

A background networking extension would ordinarily never be allowed to present system UI or communicate with PassKit daemons. Apple enables this by signing WebKit's Networking process with the private entitlement com.apple.payment.all-access. This entitlement allows the Networking process to connect directly to the system payment daemon (com.apple.passd.payment) and manage PKPaymentAuthorizationController. The controller registers an internal delegate conforming to PKPaymentAuthorizationControllerPrivateDelegate, a private protocol through which PassKit coordinates sheet presentation and merchant callbacks entirely out of process.

How Safari / WebKit does it

  • WebProcess routes payment IPC straight to the Networking process via ensureNetworkProcessConnection().
  • The Networking process holds com.apple.payment.all-access and com.apple.private.accounts.bundleidspoofing, letting it talk to com.apple.passd.payment on behalf of arbitrary host applications without UIProcess mediation.
  • PaymentAuthorizationController presents the system sheet using PKPaymentAuthorizationController and implements the private delegate protocol PKPaymentAuthorizationControllerPrivateDelegate.

What a BrowserEngineKit browser can do

  • Cannot obtain com.apple.payment.all-access. Neither host applications nor BrowserEngineKit extension processes have access to this entitlement.
  • Extension processes cannot contact com.apple.passd.payment or trigger remote payment presentation.
  • A third-party browser can only call public PassKit APIs (such as PKPaymentAuthorizationController) from its main application process, where PassKit enforces that all transactions belong to the app developer's registered merchant ID.

2Per-merchant capability checks (canMakePaymentsWithActiveCard)

Before displaying an Apple Pay button on checkout, modern websites query whether the user can actually pay. In Apple Pay JS, sites call ApplePaySession.canMakePaymentsWithActiveCard(merchantIdentifier). This allows a site to check not merely whether the device possesses payment hardware, but whether the user has at least one card in Apple Wallet that is supported by that specific merchant's processing capabilities and merchant account.

In Safari, WebKit fulfills this check by invoking the private PassKit C function PKCanMakePaymentsWithMerchantIdentifierDomainAndSourceApplication (and its predecessor PKCanMakePaymentsWithMerchantIdentifierAndDomain). WebKit forwards the website's declared merchantIdentifier, the website's domain name, and the application identifier into PassKit's private daemon. The daemon consults the user's stored passes against the merchant's criteria and returns a tailored boolean result.

Public PassKit provides no such method. Third-party developers only have access to PKPaymentAuthorizationController.canMakePayments() (which only checks device-level hardware support) or canMakePaymentsUsingNetworks:capabilities: (which checks whether the device holds cards belonging to generic card networks like Visa or Mastercard). Public APIs cannot accept an arbitrary website's merchant identifier or web domain. Without private SPI, a browser engine cannot accurately evaluate whether a given website's merchant account can accept any of the user's active cards.

How Safari / WebKit does it

  • WebPaymentCoordinatorProxy::platformCanMakePaymentsWithActiveCard passes the merchant ID and domain to private SPI PKCanMakePaymentsWithMerchantIdentifierDomainAndSourceApplication.
  • The system checks the user's Wallet specifically against the merchant's supported payment networks and restrictions.

What a BrowserEngineKit browser can do

  • Can only call public canMakePayments() or canMakePayments(usingNetworks:capabilities:).
  • Cannot supply third-party merchant IDs or web domain names to the system.
  • Must either approximate the check (risking false positives where a button appears but the card is rejected at checkout) or return false, causing sites to hide Apple Pay entirely.

Evidence

  • WebKitWebPaymentCoordinatorProxyCocoa.mm:81–96 — implementation of platformCanMakePaymentsWithActiveCard calling PKCanMakePaymentsWithMerchantIdentifierDomainAndSourceApplication.
  • DatasetSPI explorer › PKCanMakePayments search — details the private SPI functions gated by Apple-only privileges.
  • ApplecanMakePayments(usingNetworks:capabilities:) — public API accepts only card networks and capability bitmasks, without merchant IDs or domains.

3Site-customized setup prompts (openPaymentSetup)

If a customer visits an online store that accepts Apple Pay but does not yet have a qualifying payment card in their Wallet, Apple Pay JS provides ApplePaySession.openPaymentSetup(merchantIdentifier). When triggered, the device launches the Apple Wallet card provisioning flow directly from the browser, allowing the customer to add a compatible card and finish their purchase without leaving the merchant flow.

WebKit implements this website-directed provisioning using a private method on PKPassLibrary: openPaymentSetupForMerchantIdentifier:domain:completion:. By providing the merchant's ID and web domain, WebKit allows PassKit to tailor the onboarding experience to that specific retailer—for example, by presenting co-branded store card setup or filtering for card networks that the merchant explicitly supports.

Public PassKit exposes an openPaymentSetup method on PKPassLibrary, but it takes no parameters. It opens a generic, uncontextualized Wallet setup interface. Third-party browsers cannot provide the merchant-aware setup experience that web developers expect when invoking ApplePaySession.openPaymentSetup.

How Safari / WebKit does it

  • Allocates a PKPassLibrary instance and calls the private selector openPaymentSetupForMerchantIdentifier:domain:completion:.
  • Wallet setup opens pre-filtered for the merchant's requirements and domain.

What a BrowserEngineKit browser can do

  • Can only call public openPaymentSetupWithCompletionHandler:.
  • Cannot associate the setup request with a website domain or merchant identifier, offering only a generic system wallet prompt.

Evidence

  • WebKitWebPaymentCoordinatorProxyCocoa.mm:98–111 — calls private openPaymentSetupForMerchantIdentifier:domain:completion:.
  • WebKitPassKitSPI.h:404 — declares the private selector on PKPassLibrary.
  • AppleopenPaymentSetup(completion:) — public PassKit method with no merchant context parameters.

4Dynamic merchant session validation (paymentServicesMerchantURL)

Security on the web requires cryptographic proof that a website is genuine before Apple Pay will display payment totals or transmit encrypted card tokens. In the Apple Pay on the Web flow, the browser does not authenticate the merchant on its own. Instead, when the payment session starts, WebKit triggers an onvalidatemerchant event containing an Apple-provided validationURL. The merchant's backend server sends an HTTPS request to this URL with its Apple-issued merchant certificate; Apple validates the certificate and returns an opaque, signed merchant session object that the site hands back to the browser via completeMerchantValidation().

The critical link in this chain is where the browser gets the validationURL. In WebKit, the system payment controller provides it directly via a private PassKit class method: +paymentServicesMerchantURLForAPIType:isDelegated:completion: (and the earlier +paymentServicesMerchantURLForAPIType:completion:). When PassKit invokes paymentAuthorizationController:didRequestMerchantSession: on WebKit's private delegate, WebKit fetches this URL and delivers it to page JavaScript.

Public PassKit has no API for retrieving Apple's merchant validation endpoints, nor does PKPaymentAuthorizationControllerDelegate contain any merchant session callback. Public PassKit is designed exclusively for native applications, where Apple Pay requests are pre-authorized using the application's embedded code-signing certificates and Apple Developer provisioning profiles. The entire dynamic, two-legged web merchant validation protocol relies on private PassKit SPI.

How Safari / WebKit does it

  • Receives didRequestMerchantSession: from PassKit via PKPaymentAuthorizationControllerPrivateDelegate.
  • Fetches the official validation endpoint using private class method +paymentServicesMerchantURLForAPIType:isDelegated:completion:.
  • Passes the URL to page JavaScript and completes validation with the resulting PKPaymentMerchantSession.

What a BrowserEngineKit browser can do

  • Public PKPaymentAuthorizationController has no mechanism to request or supply a web merchant validation URL.
  • Third-party browsers cannot implement the standard onvalidatemerchant lifecycle expected by web checkouts.

Evidence

5Installment plans and financing configurations

When purchasing high-value items online, merchants frequently offer installment financing, such as monthly installments with Apple Card or retailer financing programs. Apple Pay JS allows merchants to declare structured installment configurations, including the annual percentage rate (APR), payment schedule, financing item details, retail channel, and program terms.

In WebKit, this is bridged to PassKit through private SPI classes: PKPaymentInstallmentConfiguration and PKPaymentInstallmentItem. In PaymentInstallmentConfiguration.mm, WebKit parses the dictionary supplied by the web page and configures private properties on these objects, including setBindingTotalAmount:, setOpenToBuyThresholdAmount:, setInstallmentMerchantIdentifier:, setInstallmentItems:, setRetailChannel:, setApr:, setProgramIdentifier:, and setProgramTerms:.

Public PassKit contains no public classes or initializers for installment configurations or installment items. The entire installment feature set in PassKit is private SPI gated by internal daemon access. Even if an alternative browser could present a basic payment sheet, it would have no mechanism to pass merchant installment plans to PassKit.

How Safari / WebKit does it

  • Allocates private PKPaymentInstallmentConfiguration and PKPaymentInstallmentItem instances.
  • Serializes web installment options (APR, threshold amounts, program terms, retail channels) and binds them to the platform payment request.

What a BrowserEngineKit browser can do

  • No public PassKit equivalents exist for installment configurations or financing items.
  • Third-party browsers cannot support web installment plans through Apple Pay.

Evidence

6The iOS delegated-request option (isDelegatedRequest)

In a recent iOS update, Apple introduced a new property on PKPaymentRequest: isDelegatedRequest. This API was designed to permit an application to present an Apple Pay payment sheet on behalf of an external merchant rather than for the app's own merchant account. WebKit added web support for this property across ApplePayRequestBase and updated its internal session resolution to request dedicated delegatedSession validation endpoints.

While this sounds promising as a theoretical path for third-party browsers, Apple's documentation and entitlement model impose strict constraints:

  • Restricted entitlement: Using isDelegatedRequest requires the application to possess the private entitlement com.apple.developer.in-app-payments-delegate.
  • Pre-registration as an Apple Pay delegate: The developer must be formally registered and approved by Apple as an Apple Pay delegate entity.
  • Platform architecture: This mechanism was created for multi-merchant e-commerce platforms and payment service providers (PSPs) who maintain formal onboarding relationships with registered merchants. It was not designed for a web browser navigating to arbitrary third-party websites across the open internet.
Furthermore, enabling isDelegatedRequest does not expose the missing web merchant validation delegates, per-site capability checks, or installment APIs. A general-purpose browser cannot use this path to act as a universal proxy for the entire web.

How Safari / WebKit does it

  • Supports isDelegatedRequest via internal PassKit hooks and resolves dedicated delegatedSession endpoints through paymentServicesMerchantURLForAPIType:isDelegated:completion:.
  • Retains full access to all private PassKit SPIs and daemon channels regardless of delegation state.

What a BrowserEngineKit browser can do

  • Cannot use isDelegatedRequest without Apple's approval and the com.apple.developer.in-app-payments-delegate entitlement.
  • Even with the entitlement, an app cannot act as a delegate for arbitrary websites that have not established a contractual delegation relationship with the browser vendor.
  • Still lacks the underlying private SPIs needed to drive the complete web payment lifecycle.

Evidence

7Real-world fallback behavior for alternative browsers

Because third-party browsers on iOS cannot drive the native Apple Pay sheet, web developers and payment gateways must handle alternative browsers differently. In practice, this creates a degraded checkout experience for users who choose an alternative browser on iOS.

When an alternative browser renders an e-commerce page:

  1. Apple's code-scan fallback flow: Apple provides a web fallback called "Apple Pay on the Web for other browsers". When a site adopts this library and detects a non-Safari browser, clicking "Apple Pay" displays a modal dialog on the screen containing a large QR code with instructions: "Scan with your iPhone camera to pay with Apple Pay". If the user is already on an iPhone running Chrome or Firefox, they are asked to scan the screen with a second Apple device or take a screenshot, introducing severe friction.
  2. Suppressed Apple Pay buttons: Most websites check ApplePaySession.canMakePayments() before rendering Apple Pay UI. If the browser returns false or fails the check, the Apple Pay button simply vanishes, and the customer is forced into manual credit card entry or third-party payment forms.
  3. Safari hand-off: Some merchants detect the browser and display an explicit prompt asking the user to copy the URL and reopen the page in Safari to complete the purchase.
This represents a major commercial and usability penalty for alternative browser engines on iOS.

How Safari / WebKit does it

  • Displays the native Apple Pay sheet directly on the screen with one-touch biometric authorization.
  • Checkout finishes in seconds without leaving the page or requiring secondary devices.

What a BrowserEngineKit browser can do

  • Users must scan an on-screen QR code with another Apple device, switch back to Safari, or abandon Apple Pay in favor of typing credit card numbers manually into web forms.

Evidence

Open questions & confidence

  • Delegated payment testing on device: While Apple introduced isDelegatedRequest in iOS 26.4 and WebKit adopted it, we have not tested whether Apple would grant com.apple.developer.in-app-payments-delegate to a general-purpose web browser. However, because delegation still requires an explicit business relationship between the delegate and each merchant, it cannot mathematically solve arbitrary web browsing across millions of uncoordinated web merchants.
  • Public Web Payment API support: Apple has not indicated plans to introduce a public BrowserEngineKit framework for web payments that would allow third-party engines to delegate merchant validation and sheet presentation to the system.
  • Main-page text verification: The analysis completely confirms the main page's description of PassKit SPIs, entitlement gating, and the structural limitations of isDelegatedRequest. The Priority remains P1 due to the commercial importance of e-commerce checkout.
  • Passkeys / WebAuthn parity: While web payments remain fully gated by Apple-private identity entitlements, public Web Authentication (passkeys) were largely closed as a capability gap via public AuthenticationServices APIs in 2022 (see WebAuthn service analysis).

Android comparison

On Android, browsers can integrate with Google Pay using the standard W3C Payment Request API. When a web page requests payment with Google Pay, any browser engine (Chromium, Gecko, or custom engines) can invoke Google Play services through public client libraries (PaymentsClient). Google Pay presents a system sheet on the user's device, authenticates the user, and returns an encrypted token for the website's merchant processor. No operating-system-exclusive entitlement or system identity spoofing is required, ensuring feature parity across all browsers on the platform.
