1Scrolling physics, rubber-banding & custom graphics stacks (BEScrollView vs. private UIScrollView SPI)

iOS users expect scrolling to feel distinctly "native": momentum deceleration must follow specific non-linear decay curves, rubber-band bouncing must smoothly absorb overscroll at boundaries, and interrupting a bounce with a new touch gesture must never cause a visual jump or stutter. In WebKit, every scrollable DOM region (the main document as well as nested overflow <div> containers) is backed by a real UIKit WKScrollView / WKChildScrollView inside WebKit's RemoteLayerTree hierarchy.

Because WebKit relies on UIKit's native scroll views for each scrollable layer, it subclasses BEScrollView via WKBaseScrollView and WKScrollView and uses private UIKit selectors to eliminate visual artifacts and coordinate nested panning (_setAvoidsJumpOnInterruptedBounce:, setTracksImmediatelyWhileDecelerating:, _setAllowsParentToBeginHorizontally:, _setAllowsParentToBeginVertically:). By contrast, alternative browser engines (Chromium, Gecko) use their own graphics and compositing stacks: they handle hit-testing, nested scroll chaining, and compositor-thread scrolling internally and paint into a single Metal surface, meaning they do not need all of the same per-view UIKit scroll primitives as Safari — though they must either approximate iOS momentum/rubber-band curves in their own physics code or coordinate an outer BEScrollView with their internal compositor.

How Safari / WebKit does it

  • WKWebViewIOS.mm configures _scrollView during initialization: if available, it calls _setAvoidsJumpOnInterruptedBounce:YES and setTracksImmediatelyWhileDecelerating:NO.
  • ScrollingTreeScrollingNodeDelegateIOS.mm mirrors these settings for asynchronous out-of-process scrolling trees and handles overscroll behavior (CSS overscroll-behavior) via private transfer methods _wk_setTransfersHorizontalScrollingToParent: and _wk_setTransfersVerticalScrollingToParent: (which invoke _setAllowsParentToBeginHorizontally: / _setAllowsParentToBeginVertically:).
  • WKScrollView.mm implements custom rubber-band restoration (_setContentSizePreservingContentOffsetDuringRubberband:) to prevent content jumping when layout size changes during an active overscroll bounce.

What a BrowserEngineKit browser can do

  • Because other browser engines use their own graphics and input stacks rather than creating a tree of nested UIScrollView instances, they handle nested scroll chaining and overscroll inside their own compositor and do not need WebKit's private parent-scroll transfer selectors.
  • Engines can adopt BEScrollView and BEScrollViewDelegate (scrollView:handleScrollUpdate:completion:) for top-level scroll integration, or drive scrolling directly from touch gestures on their composited surface.
  • If an engine uses BEScrollView directly, it lacks private selectors like _setAvoidsJumpOnInterruptedBounce:; if it drives scrolling in its own compositor, it must tune its own deceleration and rubber-band curves and coordinate scroll state with host UI bars and system gestures.

2Text input, IME composition & async editing (BETextInput vs. UITextInputPrivate)

Unlike scrolling — which an engine with its own graphics stack can handle largely inside its own compositor — text entry and Input Method Editors (IMEs) always require tight coordination with the operating system's keyboard subsystem. Entering text on iOS involves software keyboards, multi-stage IME composition and marked-text underlining for Chinese, Japanese, and Korean (CJK), predictive candidate bars, inline autocorrection bubbles, dictation streaming, and hardware keyboard shortcuts. Because browser rendering engines run in dedicated helper processes and render DOM text inside their own graphics surfaces rather than standard UITextField views, every keystroke, composition range change, candidate selection, and caret/selection bounding box must be synchronized across process boundaries.

In iOS 17.4, Apple introduced BETextInput and BETextInteraction in BrowserEngineKit to expose an asynchronous text-input contract. WebKit's source code illustrates both the progress and the remaining surface area: WebKit implements a runtime fork in -[WKContentView _updateRuntimeProtocolConformanceIfNeeded]. When modern asynchronous interaction is active, it dynamically adds the BETextInput protocol; otherwise, it dynamically registers five legacy private protocols: UIWKInteractionViewProtocol, UITextInputPrivate, UITextAutoscrolling, UITextInputMultiDocument, and _UITextInputTranslationSupport.

Why IME is a key research area: Even with BETextInput adopted in modern builds, WebKit's allowlists still retain dozens of private keyboard and IME symbols — including marked-text range selectors (setRangeInMarkedText:, setSelectedRangeInMarkedText:, setAnnotatedText:), input-method command hooks (handleKeyInputMethodCommandForCurrentEvent, addInputString:withFlags:withInputManagerHint:), direct queries to UIKeyboardImpl and UIKeyboardInputModeController (e.g. UIKeyboardEnabledInputModesAllowChineseTransliterationForText), UIWKAutocorrectionContext, and low-level GraphicsServices hardware-keyboard modifier functions. How completely BETextInput covers complex CJK IME composition, dead-key state, and live autocorrection geometry in a non-WebKit engine has not yet been verified empirically.

How Safari / WebKit does it

  • In WKContentViewInteraction.mm, WebKit dynamically registers protocol conformances at runtime. For legacy or fallback modes, it uses private UIKit interfaces like UITextInputPrivate.
  • WebKit coordinates autocorrection context via private classes UIWKAutocorrectionContext and UIWKAutocorrectionRects, querying UIKeyboardImpl.activeInstance and autocorrectSpellingEnabled.
  • For hardware keyboards, WebKit checks physical modifier keys and country layouts using private GraphicsServices symbols (GSEventIsHardwareKeyboardAttached, GSKeyboardGetModifierState, GSEventGetHardwareKeyboardCountry).
  • WebKit integrates with system Writing Tools via WTWritingToolsDelegate, supporting proofreading sessions and suggestions (WTTextSuggestion).

What a BrowserEngineKit browser can do

  • Third-party engines must conform to BETextInput and attach BETextInteraction to their content view. This gives them public asynchronous methods to handle replacement text (replaceText:withText:shouldUnderline:completion:), candidate suggestions (setCandidateSuggestions:), and document context queries (requestDocumentContext:completion:).
  • Third-party engines cannot access UIKeyboardImpl or GraphicsServices modifier functions. They rely solely on public key events delivered via BEKeyEntry, which makes it harder to detect whether a physical keyboard is attached prior to a keypress or inspect system transliteration mode flags (e.g. UIKeyboardEnabledInputModesAllowChineseTransliterationForText).
  • Architectural cost: Adopting BETextInput requires a non-trivial architectural re-engineering to make the engine's internal input stack asynchronous, handling pending completions across process boundaries.

3Selection handles, callout bars & context menus (BEContextMenuConfiguration)

Selecting text or long-pressing links on iOS surfaces floating interface elements: text selection handles with loupe magnification, the contextual edit menu bar (Cut, Copy, Paste, Share, Translate), and rich preview context menus for hyperlinks and images. Because web content layout and hit-testing occur in a helper process, determining what element was tapped and generating the preview configuration is inherently asynchronous.

Standard UIKit context menus (UIContextMenuInteraction) expect a synchronous return of a UIContextMenuConfiguration. BrowserEngineKit solves this by introducing BEContextMenuConfiguration, which can be returned immediately and fulfilled later via fulfillUsingConfiguration:. WebKit uses this public BrowserEngineKit class when configured for async interactions, but falls back to swizzling the private selector _contextMenuInteraction:configurationForMenuAtLocation:completion: when BrowserEngineKit is unavailable.

How Safari / WebKit does it

  • In WKContentViewInteraction.mm (lines 15311–15324), WebKit implements contextMenuInteraction:configurationForMenuAtLocation:. When BrowserEngineKit is enabled, it allocates a BEContextMenuConfiguration and fulfills it once the WebContent process finishes hit-testing.
  • For selection handles and magnifying loupes, WKTextInteractionWrapper.mm coordinates with UITextSelectionDisplayInteraction (accessible via [_asyncTextInteraction textSelectionDisplayInteraction]), suppressing handles during overflow scrolling with HideEditMenuScope.
  • WebKit still references legacy selection metadata classes such as WebSelectionRect and UITextSelectionRectCustomHandleInfo in its allowlist.

What a BrowserEngineKit browser can do

  • Third parties can use BEContextMenuConfiguration to display asynchronous preview context menus for web links and images, mirroring WebKit's modern path.
  • For text selection menus, third parties can use public UIEditMenuInteraction and BETextInteraction to show system edit items.
  • However, synchronizing custom handle views and suppressing selection highlights across out-of-process scroll boundaries without access to private UIKit selection container views (_managedTextSelectionViews) remains intricate and prone to visual desynchronization during fast gesture flings.

Evidence

4Drag & drop, native pickers, and Apple Pencil Scribble

Mobile web forms require native input peripherals: date and time wheels for <input type="date">, dropdown wheel lists for <select> elements, drag-and-drop sessions for images and selected text, and handwriting recognition via Apple Pencil ("Scribble") directly into form fields.

BrowserEngineKit provides BEDragInteraction, which WebKit adopts to handle drag sessions asynchronously across process boundaries. For Apple Pencil input, WebKit implements the public UIIndirectScribbleInteractionDelegate protocol, creating synthetic UIScribbleElementIdentifier tokens for web input fields and monitoring stylus availability via UIScribbleInteraction.isPencilInputExpected. For form pickers, however, WebKit still uses internal UIKit components like UIPickerContentView and private data-owner isolation (_performAsDataOwner:block:).

How Safari / WebKit does it

  • WKContentViewInteraction.mm adopts BEDragInteractionDelegate (lines 11535–11544), preparing drag sessions and adding items asynchronously as the WebContent process serializes drag data.
  • In lines 12685–12752, WebKit registers UIIndirectScribbleInteraction, allowing users to handwrite directly into HTML input controls with Apple Pencil; WKStylusDeviceObserver.mm observes UIScribbleInteraction.isPencilInputExpected.
  • Form pickers (WKFormSelectPicker.mm, WKDatePickerViewController.mm) host native UIKit pickers directly in peripheral accessory views and popovers, using private selectors like _setShowsFileSizePicker: and _performAsDataOwner:block: to control security boundaries during drag and file selection.

What a BrowserEngineKit browser can do

  • Third-party engines have access to public BEDragInteraction and public UIIndirectScribbleInteraction, allowing them to support drag sessions and Apple Pencil handwriting if they build the necessary element-tracking adapters.
  • For form controls, third parties must either render inputs entirely in HTML/DOM (which lacks native iOS haptic wheel feedback and visual styling) or construct custom UIKit picker view controllers from scratch using public UIPickerView and UIDatePicker within their own popovers.
  • Third parties lack access to _performAsDataOwner:block:, which enforces enterprise managed data separation (managed open-in) during clipboard and drag operations.

5Viewport obscuring, keyboard avoidance & SpringBoard status bar styling

When browsing on iOS, top address bars and bottom navigation toolbars dynamically shrink and expand as the user scrolls. When an input field is tapped, the virtual keyboard animates upward. In all these cases, the web viewport, safe area insets (e.g. CSS env(safe-area-inset-top)), and dynamic viewport units (dvh, svh, lvh) must update synchronously without causing the page content to jump jarringly under the user's thumb.

WebKit solves this with private view-coordination hooks. In WKWebViewIOS.mm, Safari sets _setObscuredInsets:, allowing the browser chrome to overlay the web view while WebKit automatically calculates the visible content area and offsets scroll targets. For keyboard presentation, WKScrollView.mm overrides _adjustForAutomaticKeyboardInfo:animated:lastAdjustment: and queries UIPeripheralHost's private method getVerticalOverlapForView:usingKeyboardInfo: to compute exact pixel overlap before animating. Additionally, Apple signs WebKit's GPU process with private SpringBoard entitlements to manage system capture status bar pills.

How Safari / WebKit does it

  • WKWebViewIOS.mm provides -[WKWebView _setObscuredInsets:] (lines 264–297, 4555), directly updating viewport layout insets, dynamic viewport units, and scroll limits without triggering unneeded re-layouts.
  • In WKScrollView.mm (lines 455–479), WebKit intercepts automatic keyboard adjustments via _adjustForAutomaticKeyboardInfo:animated:lastAdjustment:, computing _keyboardBottomInsetAdjustment via private class UIPeripheralHost and adjusting _systemContentInset.
  • WKContentViewInteraction.mm checks self._scroller.firstResponderKeyboardAvoidanceEnabled (line 8721) to defer scrolling to focused elements until keyboard appearance animations begin.
  • WebKit's GPU process holds private entitlement com.apple.springboard.statusbarstyleoverrides, allowing MediaCaptureStatusBarManager.mm to display system status bar pills for active WebRTC media capture.

What a BrowserEngineKit browser can do

  • Third-party engines cannot invoke _setObscuredInsets: or UIPeripheralHost. They must rely on public keyboard notifications (UIKeyboardWillShowNotification) and adjust their root view frames or scroll insets manually. Because UIKit keyboard notifications often lag behind interactive gesture transitions, this frequently causes visual jitter or sluggish content repositioning.
  • Third-party browsers cannot obtain com.apple.springboard.statusbarstyleoverrides (an Apple-private, WebKit-exclusive entitlement), meaning they cannot register custom status bar style overrides for media capture; iOS manages standard capture indicators on their behalf.

6Churn risk & allowlist fragility: the 2026 momentum bounce regression

The extent to which WebKit still relies on private UIKit SPIs is vividly illustrated by WebKit's own SPI allowlist architecture and recent git history. While Apple has created modern allowlists (AllowedSPI.toml) for approved or transitioning symbols, the vast majority of UIKit SPIs remain isolated in AllowedSPI-legacy.toml. Out of 282 SPIs in the "UIKit Views, Scrolling, Gestures & Text Input" category, 282 (97.2%) remain in the legacy allowlist, with only 8 in the active allowlist.

When WebKit engineers attempt to eliminate these legacy private selectors, subtle behavioral regressions frequently occur. In January 2026, WebKit commit f0db2bb7cc96 (2026-01-14) attempted to remove private momentum selectors _setAvoidsJumpOnInterruptedBounce: and setTracksImmediatelyWhileDecelerating: in favor of a newer API property (_setDecelerationTrackingBehavior:). Just three weeks later, commit 2a02830783a0 (2026-02-04) had to completely revert the change with the note: "Our adoption of setDecelerationTrackingBehavior broke scrolling during an existing momentum phase on certain HTML content in Mail.app." Both private selectors were immediately restored to AllowedSPI-legacy.toml. You can explore the full history of such restorations in the Legacy Policy Analysis section of the SPI dataset.

Implication for alternative engines: An engine that drives its own scrolling physics inside its own graphics pipeline does not directly depend on _setAvoidsJumpOnInterruptedBounce: the way WebKit's UIScrollView-based tree does. However, the sheer volume of ongoing churn in WebKit's UIKit integration shows how many subtle OS assumptions exist at the boundary between web content and UIKit gestures, keyboards, and system overlays.

7Accessibility & cross-process VoiceOver integration (AXRemoteElement vs. public APIs)

Accessibility is one of the most architecturally sensitive integration points for a browser engine that renders into its own graphics surface in a separate process. Because the DOM and layout tree live inside the sandboxed WebContent process while the host view hierarchy lives in the UI process, iOS assistive technologies (VoiceOver, Switch Control, Voice Control, Full Keyboard Access, Speak Selection) need a way to traverse thousands of virtual DOM nodes, map their coordinates through scrolled layers, read rich text attributes, and dispatch actions across process boundaries.

WebKit accomplishes this on iOS using 53 private SPIs in the Accessibility & Speech Synthesis category (plus additional accessibility selectors in UIKit), a 3,500-line wrapper in WebAccessibilityObjectWrapperIOS.mm, and private cross-process Mach/UUID handshakes with Apple's system accessibility runtime (AXRuntime.framework and com.apple.iphone.axserver). While newer iOS releases have begun introducing BEAccessibility* helpers (such as browserAccessibilityValueInRange:, browserAccessibilitySelectedTextRange, and BEAccessibilityContainerTypeFieldset), WebKit itself still relies heavily on private cross-process bridging and private accessibility tokens — making accessibility a major open area for research on non-WebKit engines.

How Safari / WebKit does it

  • In WKContentView.mm (lines 798–834), storeAccessibilityRemoteConnectionInformation attaches private associated-object keys (@"ax-uuid" and @"ax-pid") to the UI-process view and sends registerUIProcessAccessibilityTokens to the WebContent process.
  • In WebPageIOS.mm (lines 780–816), the WebContent process creates a WKAccessibilityWebPageObject and invokes the private selector setRemoteTokenDictionary: (injected by the system accessibility bundle) with @{ @"ax-pid": ..., @"ax-uuid": ..., @"ax-register": @YES }, and for remote subframes instantiates private AXRemoteElement (initWithUUID:andRemotePid:andContextId: in AccessibilityObjectIOS.mm:190).
  • WebAccessibilityObjectWrapperIOS.mm annotates rich text and DOM semantics using private AXRuntime tokens (UIAccessibilityTokenBlockquoteLevel, UIAccessibilityTokenLanguage, UIAccessibilityInlineTextCompletion, _accessibilityUnregister) and observes _AXS* system accessibility notifications forwarded via the private entitlement com.apple.private.darwin-notification.introspect.

What a BrowserEngineKit browser can do

  • BrowserEngineKit has added public accessibility support methods on text and container elements (which WebKit partially adopts in WebAccessibilityObjectWrapperIOS.mm via browserAccessibilityValueInRange:, browserAccessibilityInsertTextAtCursor:, etc.).
  • However, an alternative engine using its own graphics stack has no native UIKit subviews for DOM elements and must expose its entire virtual accessibility tree either by mirroring/proxying nodes into the UI process or using whatever cross-process remote-element hooks BrowserEngineKit publicly supports.
  • Whether public UIAccessibility and BEAccessibility* APIs are sufficient for full VoiceOver parity (out-of-process iframes, rotor navigation, braille tables, rich text attributes, and low-latency tree updates) without AXRemoteElement and AXRuntime SPIs requires dedicated investigation.

Android comparison

On Android, browser engines ship their own input and gesture stacks directly. Android applications create a custom SurfaceView or TextureView and interact with the operating system through public platform APIs: InputMethodManager and InputConnection for software keyboard input, AccessibilityNodeProvider for accessibility, and OverScroller for momentum physics. Third-party engines like Blink/Chromium and Gecko implement their own physics decay formulas and gesture recognizers, operating as first-class peers to the system browser. On iOS, by contrast, touch gestures, momentum physics, and text input are deeply entangled with private UIKit internals, making it impossible for third-party engines to achieve identical feel without access to the same private selectors WebKit uses.
