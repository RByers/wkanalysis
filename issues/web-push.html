1The webpushd architecture & BrowserEngineKit daemon asymmetry

Web Push allows websites to receive updates and display notifications even after the user has navigated away or closed the browser tab. On iOS, WebKit does not handle push notifications within the browser app process itself. Instead, Apple routes push events through a dedicated background system daemon called webpushd, a persistent launchd daemon that outlives individual browser sessions.

By contrast, Apple’s BrowserEngineKit (iOS 17.4+) exposes exactly three extension types for alternative third-party browser engines: WebContent, GPU, and Networking. Crucially, it does not provide a background daemon process. A third-party engine cannot spawn an equivalent background daemon to handle incoming push messages asynchronously.

Furthermore, third-party engines are expressly prohibited from routing their push registrations through Safari's existing webpushd daemon. Connecting to webpushd over XPC requires the calling process to hold the Apple-private com.apple.private.webkit.webpush entitlement, and the daemon explicitly enforces a hardcoded bundle identifier allowlist (allowing only com.apple.SafariViewService and other Apple system components).

Architecturally, webpushd runs under an adaptive transaction model (configured via com.apple.webkit.webpushd.ios.plist) and listens on Mach service com.apple.webkit.webpushd.service. Crucially, the daemon's sandbox profile (com.apple.WebKit.webpushd.sb.in) contains no network socket privileges: it has zero outbound TCP or UDP access. All communication with the outside world is mediated entirely over Mach IPC to Apple's system push daemon (com.apple.apsd). To communicate with webpushd, a client process must hold the Apple-private entitlement com.apple.private.webkit.webpush, which WebKit verifies on incoming Mach connections before processing any command.

How Safari / WebKit does it

  • webpushd is launched by launchd under the mobile user account with transaction management (EnableTransactions) and adaptive process lifetime.
  • WebKit's Network Process holds the Apple-private entitlement com.apple.private.webkit.webpush in process-entitlements.sh, allowing it to open Mach connections to com.apple.webkit.webpushd.service.
  • The daemon operates with strict sandboxing: no network sockets, communicating with Apple push services exclusively via Mach lookups to com.apple.apsd.

What a BrowserEngineKit browser can do

  • Third-party browsers holding BrowserEngineKit entitlements cannot obtain com.apple.private.webkit.webpush and cannot communicate with webpushd.
  • BrowserEngineKit does not provide an equivalent system daemon or background extension point that survives browser process termination.
  • A third-party browser must rely on standard iOS application mechanisms: registering for remote notifications in the host app and processing incoming pushes within an App Extension.

2Push endpoints: per-site web.push.apple.com tokens vs. an app APNs token

Under the W3C Push API standard, when a web page calls registration.pushManager.subscribe(), the browser returns a unique push endpoint URL. An application server sends HTTP POST requests to that endpoint containing encrypted payloads. On Safari, these endpoints point directly to Apple's push infrastructure (https://web.push.apple.com/…).

WebKit achieves this by querying Apple's internal push framework directly. Inside webpushd, the daemon holds the Apple-private entitlement aps-connection-initiate, which allows it to call private APSConnection SPIs. When subscribing an origin, webpushd creates an APSURLTokenInfo instance with the web topic and Voluntary Application Server Identification (VAPID) public key, and invokes requestURLTokenForInfo:completion: on its APSConnection. Apple's push daemon generates an individualized endpoint URL for that website. Third-party applications on iOS cannot call these SPIs; they have only a single, app-wide 32-byte APNs device token returned by UIApplication.shared.registerForRemoteNotifications().

How Safari / WebKit does it

  • webpushd holds aps-connection-initiate, allowing direct communication with apsd through private APSConnection interfaces.
  • Calls -[APSConnection requestURLTokenForInfo:completion:] with the site topic and VAPID key to obtain a unique web.push.apple.com endpoint.
  • Apple's push service directly manages per-site subscription endpoints without any browser vendor relay server.

What a BrowserEngineKit browser can do

  • Cannot obtain aps-connection-initiate; raw APSConnection calls are rejected by the system.
  • The browser app possesses only a single device-level APNs push token for the application itself.
  • To provide Web Push endpoints, the browser vendor must host a custom push relay server (e.g., push.browser-vendor.com/…) that receives W3C Web Push HTTP POST requests and translates them into APNs pushes directed to the browser app's token.

3Waking the service worker: UnboundedNetworking assertions vs. extension limits

Under the W3C specification, receiving a push message wakes the website's Service Worker and fires a JavaScript push event (self.addEventListener('push', ...)). The worker can execute arbitrary asynchronous code—such as querying an IndexedDB store or fetching updated data from an API—before deciding whether and how to call self.registration.showNotification(...).

WebKit accomplishes this on iOS by having webpushd wake the host application via FrontBoard (the system window and application lifecycle manager). Upon waking, WebKit's UIProcess immediately takes a RunningBoard process assertion of type UnboundedNetworking labeled "WebKit Process Push Event" in NetworkProcessProxy.cpp. This grants a 20-second execution window. The Network Process then passes the push event to SWServer::processPushMessage, which spins up or contacts the WebContent process hosting the service worker and executes the JavaScript handler.

A third-party browser receiving an APNs push cannot replicate this. When an APNs push arrives with mutable-content: 1, iOS wakes the app's public UNNotificationServiceExtension (NSE). However, an iOS App Extension runs in a severely restricted sandbox: it cannot spawn BrowserEngineKit child processes (such as BEWebContentProcess or BENetworkingProcess). Even if process spawning were permitted, an extension is governed by a strict Jetsam memory cap (typically 15–30 MB) and a hard execution timeout (~30 seconds). Initializing a modern browser engine (Blink/V8 or Gecko/SpiderMonkey) within those constraints is technically impossible.

How Safari / WebKit does it

  • webpushd wakes the target web app host using FrontBoard background options (FBSActivateForEventOptionTypeBackgroundContentFetching).
  • NetworkProcessProxy::processPushMessage takes an UnboundedNetworking assertion ("WebKit Process Push Event") with a 20-second timeout.
  • SWServer::processPushMessage boots the service worker execution context in a WebContent process to run arbitrary JavaScript push event listeners.

What a BrowserEngineKit browser can do

  • The push wakes a public UNNotificationServiceExtension, which cannot launch BrowserEngineKit helper processes.
  • The extension cannot run the website's JavaScript service worker due to memory constraints (~15–30 MB Jetsam limit) and execution deadlines.
  • The notification must be generated declaratively: the push payload itself must contain the notification title, body, and icon, rather than being synthesized by dynamic web script.

4Payload decryption (RFC 8291) and key persistence

Web Push payloads are end-to-end encrypted under RFC 8291 ("Message Encryption for Web Push") using Elliptic Curve Diffie-Hellman (ECDH) on the P-256 curve and either AES-128-GCM or AES-GCM. The browser generates the encryption keys when the site subscribes, and only the browser can decrypt incoming payloads.

In WebKit, encryption keys are held in a persistent SQLite database managed by webpushd (located at ~/Library/WebKit/WebPush/PushDatabase.db). When apsd delivers an incoming push message to webpushd, the daemon adopts an OS transaction (os_transaction_create("com.apple.webkit.webpushd.push-service.incoming-push")), queries the database for the topic's client private key and auth secret, and decrypts the payload directly in C++ via decryptAES128GCMPayload or decryptAESGCMPayload before any web process is contacted.

For a BrowserEngineKit browser, decryption must take place inside the Notification Service Extension before presenting the notification to the user. Because the extension runs in an isolated process separate from the main browser app, subscription keys cannot be stored in the app's private sandbox. Instead, the browser must store its Web Push keys in a shared App Group container (group.<bundle_id>) accessible to both the main browser process and the extension process. When the extension wakes, it reads the encrypted APNs payload, loads the matching key pair from the shared container, and performs the RFC 8291 decryption.

How Safari / WebKit does it

  • Client keys (P-256 private key and authentication secret) are stored in webpushd's centralized PushDatabase.db.
  • PushService::didReceivePushMessage creates an OS transaction, loads the subscription record, and decrypts the payload inside the daemon using PushCrypto.
  • Decrypted payload bytes are forwarded to the web app's process over local IPC.

What a BrowserEngineKit browser can do

  • Must store Web Push keys in an App Group container shared between the main browser app and its Notification Service Extension.
  • The Notification Service Extension loads the private keys and performs RFC 8291 AES-GCM decryption in memory during the brief notification interception window.
  • This decryption architecture is technically feasible using public cryptography libraries (e.g. CryptoKit or standard WebCrypto implementations).

Evidence

5Notification identity and permissions: synthetic push bundles vs. app-wide settings

On iOS, Safari does not support Web Push for websites open in ordinary browser tabs. WebKit's source code contains an explicit architectural lockout: in WebPushDaemon::handleIncomingPush and notifyClientPushMessageIsAvailable, webpushd verifies that the subscription's pushPartition (which holds the WebClip identifier for Home Screen web apps) is non-empty. If pushPartition is empty, webpushd logs an error ("Cannot notify client app about web push action with empty pushPartition string") and drops the push entirely.

For Home Screen web apps, webpushd relies on Apple-private entitlements to synthesize distinct system identities. Holding com.apple.usernotification.notificationschedulerproxy and com.apple.private.usernotifications.app-management-domain.proxy (configured to com.apple.WebKit.PushBundles), webpushd instantiates UNUserNotificationCenter with a synthetic bundle ID: com.apple.WebKit.PushBundle.<pushPartition>. Because of this proxy entitlement, each installed web app appears in the iOS Settings app as an independent entry with its own notification toggle, icon, and alert settings.

A third-party browser attempting to deliver Web Push for ordinary browser tabs has no access to these proxy entitlements. It can only schedule notifications through standard public UNUserNotificationCenter APIs under its own application bundle ID. As a result, all web notifications display the browser's application icon and name (e.g., "Chrome" or "Firefox") rather than the website's standalone identity. In iOS Settings, the user has only a single, app-wide notification permission toggle: disabling notifications for the browser silences every subscribed website at once.

How Safari / WebKit does it

  • WebKit on iOS deliberately excludes ordinary browser tabs: pushes with an empty pushPartition are dropped. Web Push is exclusively offered to web apps installed to the Home Screen.
  • webpushd holds com.apple.usernotification.notificationschedulerproxy and com.apple.private.usernotifications.app-management-domain.proxy.
  • Posts notifications under synthetic bundle IDs (com.apple.WebKit.PushBundle.<id>) using UIWebClip metadata, granting each web app its own icon and independent entry in iOS Notification Settings.

What a BrowserEngineKit browser can do

  • Can offer Web Push for ordinary browser tabs, which Safari does not support on iOS.
  • Must post all notifications through the browser's own UNUserNotificationCenter, appearing under the browser app's icon and bundle identifier.
  • Web origin identity can only be shown in notification text (e.g. a subtitle reading "from example.com").
  • Users have only a single global notification toggle for the browser app in iOS Settings; per-site permission toggles must be managed within the browser's own in-app settings UI.

6The Android-style relay model for BrowserEngineKit browsers

On Android, mobile browsers have long supported Web Push for ordinary browser tabs without requiring web app installation. They do this by acting as the push client: the browser vendor runs a cloud push relay (such as Firebase Cloud Messaging for Chrome), issues relay endpoints to subscribing websites, receives push messages through the OS push client, and displays notifications under the browser application.

A BrowserEngineKit browser can implement this identical architectural pattern on iOS using public APIs:

  1. Vendor Push Relay: The browser vendor operates a public push relay server. When a website calls pushManager.subscribe(), the browser sends its app-level APNs device token and an internal subscription ID to its relay, returning a vendor endpoint URL (e.g. https://push.browser.com/sub/xyz) to the web page.
  2. APNs Ingestion: When the website's application server posts an RFC 8291 encrypted message to the vendor endpoint, the relay converts it into an APNs remote push notification directed to the browser app's token, setting mutable-content: 1 in the aps dictionary.
  3. Extension Decryption: iOS delivers the push to the browser's UNNotificationServiceExtension. The extension reads the encrypted payload, fetches the decryption keys from the shared App Group container, decrypts the payload, and builds a UNNotificationContent object.
  4. Presentation: The extension delivers the notification to the system via contentHandler(bestAttemptContent), showing the website's title, body, and origin attribution.
The Declarative Web Push constraint: Because the Notification Service Extension cannot spin up browser engine processes to run a service worker, this model can only display notifications whose content is provided directly in the push payload. Websites that rely on running arbitrary JavaScript during a push event (e.g., calling fetch() to retrieve confidential data after receiving an empty ping) cannot function under this architecture. However, it provides full compatibility with the emerging W3C Declarative Web Push standard and standard payload-bearing notifications.

How Safari / WebKit does it

  • Does not offer Web Push to ordinary browser tabs on iOS at all.
  • Installed web apps use Apple's native infrastructure: zero vendor relay servers, direct web.push.apple.com endpoints, and full background service worker execution via webpushd and RunningBoard assertions.

What a BrowserEngineKit browser can do

  • Can successfully bring Web Push to ordinary tabs on iOS by operating an external APNs push relay server.
  • Relies exclusively on public APIs: UIApplication remote notifications, UNNotificationServiceExtension, and App Groups.
  • Cannot run background JavaScript in service workers; notifications are restricted to payload-derived content.
  • The browser vendor bears the ongoing infrastructure and operational cost of maintaining a global push relay service.

Open questions & confidence

  • Public workaround untested on iOS: While the APNs + Notification Service Extension + App Group architecture is widely used by messaging applications and technically compatible with BrowserEngineKit browser architectures, no third-party browser has publicly deployed this Web Push relay pipeline on iOS to date. Practical edge cases—such as APNs delivery latency, extension memory limits under high push volume, or background termination behaviors—remain untested on real devices.
  • Silent push limitations: W3C Web Push permits "silent" pushes where no user-visible notification is displayed. On iOS, background pushes that do not show a notification (e.g. content-available: 1 without user alert) are heavily deprioritized and throttled by the Duet Activity Scheduler (dasd) based on battery and usage patterns. If an NSE fails to present a notification before its deadline expires, iOS displays the original unedited notification payload, making reliable silent push practically impossible for third-party browsers.
  • Main-page alignment: Our source analysis confirms the main page's description. Safari's webpushd is architected specifically around installed Home Screen web apps and relies on private entitlements (aps-connection-initiate, notificationschedulerproxy, com.apple.private.webkit.webpush). Third-party browsers cannot use WebKit's native daemon, but can achieve tab-level Web Push through an external relay and public UserNotifications extensions with the trade-offs documented above. We maintain the Priority at P2 and Confidence at High.

Android comparison

On Android, Web Push for ordinary browser tabs has been supported for nearly a decade. When a user grants notification permissions to a website in Chrome, Chrome registers with Firebase Cloud Messaging (FCM) and returns an FCM push endpoint. When a push message arrives, Android wakes Chrome's background service. Chrome can initialize its network and JavaScript runtime in the background, dispatch a full push event to the website's service worker, and display a notification that attribution metadata ties directly to the originating website.

On iOS, by contrast, Apple's platform architecture restricts background execution and notification synthesis. Safari relies on private daemons and RunningBoard assertions to wake service workers exclusively for Home Screen web apps. A third-party browser on iOS can deliver Web Push to tabs, but must substitute an external push relay for FCM and is restricted to payload-only notifications displayed under the browser's own application bundle.
