Capability gap

Background execution: uploads, downloads & tab survival

Priority P2 Confidence High(Confirmed across WebKit assertion logic and APIs) On Android? Mostly (Foreground services and OS grouping allow equivalent priority adjustments)

In one sentence: When a user switches apps, Safari uses Apple-private RunningBoard assertions to keep background uploads running and protect inactive tabs from Jetsam memory kills, while a third-party browser is forced to let uploads time out and tabs reload, though iOS 18.2 introduced BEDownloadMonitor to partially bridge the gap for file downloads.

What this page adds: WebKit's source code shows how the engine relies on private entitlements and process-management SPIs to manipulate Jetsam memory bands and networking assertions. While Apple closed the file-download gap via the public BEDownloadMonitor, AssertionCapability.mm explicitly strips any attempt by a third-party browser extension to request "UnboundedNetworking" or "BoostedJetsam" capabilities, leaving uploads and background tabs vulnerable to immediate suspension.

1Process suspension and the socket failure mode

On iOS, when the user switches to another app or locks the phone, the app they left is given a short grace period (roughly 30 seconds) and is then suspended: its threads stop running and its network sockets go idle. A download that the browser is performing in one of its own processes simply stops making progress until the user comes back. If the connection times out in the meantime the download fails.

Technically, this is decided by RunningBoard (the iOS process-lifecycle daemon). A process stays runnable in the background only while something holds an assertion on it. Apps get a time-limited "Background" assertion when they leave the foreground; anything longer needs a specific grant. WebKit models these as ProcessAssertionType values and translates them to RunningBoard assertion names such as Background, UnboundedNetworking, MediaPlayback and BoostedJetsam in the com.apple.webkit domain.

Evidence

  • WebKitProcessAssertionCocoa.mm:338–384 — maps each ProcessAssertionType to its RunningBoard name and domain; the comment on line 343 notes that "background assertions time out after 30 seconds on iOS".
  • WebKitProcessAssertion.h:66 — the UnboundedNetworking assertion type.
  • DatasetEntitlements explorer › Process Lifecycle asymmetry card — overview of the RunningBoard-related entitlements WebKit's processes carry.

When an upload cannot be completed within iOS's standard background grace period, the consequences for the web user and web application are severe: the upload freezes mid-transfer, times out, and crashes with an unrecoverable network error.

While the client is frozen in the background, several failure modes occur in sequence:

  • Server-side timeout: Upstream web servers and intermediate reverse proxies (such as NGINX, Cloudflare, or AWS load balancers) maintain strict HTTP request and TCP keep-alive timers (typically 30 to 60 seconds). When client packets cease flowing, the server sends a TCP RST or FIN packet to close the stalled socket.
  • Socket reset on resume: When the user eventually switches back to the browser app, RunningBoard resumes thread execution. The networking process attempts to write the next buffered chunk to the socket, immediately encountering a broken pipe (EPIPE) or connection reset by peer (ECONNRESET).
  • Web API failure: The network stack reports a transfer error up to WebContent. In modern web standards, the pending fetch() promise is rejected with a TypeError: Failed to fetch (or TypeError: Load failed in WebKit). For XMLHttpRequest, the instance fires an error event (onerror) or abort event. If the web page lacks complex custom chunk-resumption logic, the user's uploaded form or media file is lost and must be started over.
  • Jetsam termination: If other foreground apps consume substantial memory while the browser is in the background, iOS's kernel memory daemon (jetsam) prioritizes suspended processes for termination. If the WebContent process is jetsammed, the tab crashes completely, losing all transient form inputs.

Evidence

  • WebKitProcessAssertionCocoa.mm:343 — source comment confirming that "background assertions time out after 30 seconds on iOS".
  • DatasetEntitlements explorer › Process Lifecycle asymmetry card — details on background expiration and jetsam suspension mechanics.

2Downloads: The BEDownloadMonitor API (iOS 18.2+)

This is the part the main-page summary under-states. BrowserEngineKit added a public class, BEDownloadMonitor, that lets a browser engine tell the system "this network task is a user-visible file download going to this destination". Once registered, the system's activity scheduler keeps the download's process alive on the engine's behalf, so the engine no longer needs the private assertion at all.

Crucially, WebKit's own iOS code path now uses exactly this mechanism. In October 2024 WebKit removed its Networking-process download assertions with the commit message "now that dasd is taking this assertion for us" (dasd is the Duet Activity Scheduler daemon). On device builds of iOS, enableModernDownloadProgress() returns true, every download task is wrapped in a WKModernDownloadProgress object that owns a BEDownloadMonitor, and beginMonitoring: is called when the download starts. The UIProcess-side assertion in DownloadProxyMap is compiled out on the same builds.

Implication: on iOS 18.2 or later, a BrowserEngineKit browser that routes its downloads through BEDownloadMonitor is using the same system path as Safari. The hard "downloads stall" gap described on the main page applies to older iOS versions, to engines that do not adopt the API, and to transfers that are not downloads (see background uploads).

How Safari / WebKit does it

  • Download::publishProgress creates a WKModernDownloadProgress for the NSURLSessionDownloadTask, passing the source URL, destination URL and an optional Live Activity access token.
  • WKModernDownloadProgress allocates a BEDownloadMonitor, calls initWithSourceURL:destinationURL:observedProgress:liveActivityAccessToken:, optionally useDownloadsFolderWithPlaceholderType:finalFileCreatedHandler:, then beginMonitoring:; resuming a download calls resumeMonitoring:completionHandler:.

What a BrowserEngineKit browser can do

  • The same. BEDownloadMonitor and BEDownloadMonitorLocation are public BrowserEngineKit API (iOS 18.2+), designed to be called from the engine's networking extension. The engine must still implement the HTTP transfer itself (e.g. with its own network stack), but the process-lifetime problem is handled by the system.
  • Adoption requires the engine to express each download as an NSProgress and a destination file URL, which is a modest integration task for a Chromium- or Gecko-based engine.

Evidence

  • Commitc804c90d7236 (2024-07-19) "Report network download progress" — introduces the HAVE(MODERN_DOWNLOADPROGRESS) path built on BEDownloadMonitor.
  • Commitb95877fdcedb (2024-10-07) "WebKit no longer needs to take unbounded network assertions on the network process for downloads … now that dasd is taking this assertion for us" — deletes the Networking-process DownloadMap assertion logic.
  • WebKitWKDownloadProgress.mm:47–60 — enableModernDownloadProgress() is true on device iOS; activityAccessToken() calls [BEDownloadMonitor createAccessToken].
  • WebKitWKDownloadProgress.mm:78–93 and :132–140 — beginMonitoring:, resumeMonitoring: and the BEDownloadMonitor initialiser.
  • WebKitDownloadCocoa.mm:164–186 — chooses the modern BEDownloadMonitor path over the legacy NSProgress publishing path.
  • AppleDownloading files in a web browser with an alternative browser engine and BEDownloadMonitor — public BrowserEngineKit documentation.

Two user-visible niceties ride on the same mechanism. First, Safari can show a greyed-out placeholder file in the Files app's Downloads folder while a download is in progress, which turns into the real file when it completes. Second, download progress can be surfaced as a Live Activity (the Dynamic Island / Lock Screen progress indicator) using an access token minted by the system.

Both come from BEDownloadMonitor: useDownloadsFolderWithPlaceholderType:finalFileCreatedHandler: asks the system to manage the placeholder and reports back the final file location (as a BEDownloadMonitorLocation with a security-scoped bookmark), and createAccessToken provides the Live Activity token that WebKit forwards from the UIProcess to the Networking process. Because these are public BrowserEngineKit calls, a third-party engine can offer the same placeholder and progress experience. WebKit fixed a bug in September 2025 where service-worker-initiated downloads were not using this path, showing it is actively maintained.

Evidence

  • WebKitWKDownloadProgress.mm:117–140 — placeholder handling via useDownloadsFolderWithPlaceholderType: and the final-file-created handler.
  • WebKitDownloadProxyCocoa.mm:43–52 — the UIProcess creates a minimal bookmark for the destination and sends PublishDownloadProgress with the Live Activity access token to the Networking process.
  • Commit465721e59955 (2025-09-04) "Service worker downloads are not being saved to Downloads folder".
  • AppleBEDownloadMonitorLocation.

3Downloads: Safari's classic UnboundedNetworking assertion

From 2019 onward, WebKit's answer was to have the browser app itself (the "UIProcess", i.e. Safari) take an UnboundedNetworking assertion on its own process for as long as at least one download is active. That assertion type is reserved for system apps: RunningBoard only honours it if the calling process is signed with the Apple-private entitlement com.apple.multitasking.systemappassertions.

How Safari / WebKit does it

  • DownloadProxyMap checks at construction whether the host process has com.apple.multitasking.systemappassertions; if so, the first download creates a ProcessAssertion of type UnboundedNetworking (reason string "WebKit downloads") and the last download finishing releases it.
  • WebKit's own Networking process is also signed with the same entitlement by Apple's build script, so historically both the app and the Networking process held the assertion (added to "avoid races" in 2019).
  • This code is now compiled only when HAVE(MODERN_DOWNLOADPROGRESS) is off, i.e. it is the legacy path (see aspect 3).

What a BrowserEngineKit browser can do

  • Nothing equivalent. com.apple.multitasking.systemappassertions is not among the six BrowserEngineKit entitlements and is not available to third-party apps, so a request for an UnboundedNetworking assertion would be refused.
  • A third-party browser gets only the standard time-limited background grace period and the public background-task APIs (beginBackgroundTask / BGTaskScheduler), which do not keep a socket alive indefinitely.

Evidence

  • WebKitDownloadProxyMap.cpp:52–54 — the processHasEntitlement("com.apple.multitasking.systemappassertions") check, guarded by !HAVE(MODERN_DOWNLOADPROGRESS).
  • WebKitDownloadProxyMap.cpp:92–96 — taking the "WebKit downloads" UnboundedNetworking assertion on the UIProcess when the first download starts.
  • WebKitprocess-entitlements.sh:634 — Apple's signing script grants the entitlement to the iOS Networking process.
  • Commit27d6db6681de (2019-03-08) "Have the UIProcess take the UnboundedNetworking assertion when downloads are in progress"; 0cc1a40179a6 (2019-05-17) "Avoid races in taking networking assertions for downloads by having both Networking and UIProcess do it".
  • DatasetEntitlements explorer › com.apple.multitasking.systemappassertions — full dossier (category: Apple-private; iOS parity: WebKit-exclusive).

4The background NSURLSession fallback

On iOS versions before 18.2 (or if an engine chooses not to adopt BEDownloadMonitor), the only public way to keep a download going after the app is suspended is to hand the URL to iOS's background download service: a background-configured NSURLSession, whose transfer is performed by a system daemon outside the app and delivered to the app when it completes.

This works, but the transfer then runs outside the browser engine. It uses Apple's networking stack rather than the engine's own, so the engine's cookies, HTTP cache, proxy configuration, certificate handling and any custom protocol behaviour (for example HTTP/3 or QUIC settings in the engine's stack) do not apply unless the browser manually copies cookies and headers into the request. The browser also loses fine-grained control over the transfer while it is in flight. For a WebKit-based browser this is less of an issue because WebKit already uses NSURLSession for all networking; for an engine with its own stack it is a visible seam.

Evidence

  • WebKitDownloadCocoa.mm:179–186 — WebKit's legacy path (non-device builds) publishes an NSProgress for the task rather than using a background session; WebKit itself never needed the background-session workaround because it had the private assertion.
  • AppleURLSessionConfiguration.background(withIdentifier:) — the public background transfer API.
  • DatasetEntitlements explorer › Process Lifecycle — the analysis page's description of public alternatives.

iOS provides a public API designed for background data transfers: NSURLSessionConfiguration.background(withIdentifier:). However, this system service was designed for native app asset sync, not general-purpose web browsing, and imposes technical constraints that make it unusable for web page uploads.

How Safari / WebKit does it

  • Safari never routes web page uploads through background NSURLSession tasks.
  • WebKit executes all HTTP uploads directly inside its own NetworkProcess using its standard network stack.
  • The private UnboundedNetworking assertion keeps the process alive in place, ensuring seamless compatibility with streamed request bodies, WebCore cookie jars, and JavaScript callbacks.

What a BrowserEngineKit browser can do

  • Cannot use background NSURLSession for streamed or dynamic web uploads. Background sessions strictly require on-disk files via uploadTask(with:fromFile:); memory data and stream tasks are forbidden by Apple's API contract.
  • Bypasses the engine's network stack: the transfer is performed out-of-process by Apple's nsurlsessiond daemon, ignoring engine-specific HTTP/3, QUIC, proxy, certificate, and cookie state.
  • Requires awkward out-of-band app-lifecycle delegates (handleEventsForBackgroundURLSession:) that cannot easily resume a suspended WebContent JavaScript execution context.

Specifically, Apple's documentation for background upload tasks explicitly states:

Apple API Requirement: "Upload tasks from data or streams are not supported in background sessions. You must upload from a file." Attempting to initiate an upload from an in-memory NSData buffer or an NSInputStream in a background session raises a runtime exception or immediate error.

In modern web applications, uploads are rarely simple standalone files on the filesystem. They frequently use the Fetch API with upload streaming (ReadableStream bodies), FormData objects composed dynamically from canvas elements (toBlob()) or media recording snippets, or encrypted payload chunks generated on the fly. To use background NSURLSession, an alternative browser engine would have to intercept every fetch request, buffer the entire stream to a temporary file on disk, launch the transfer through nsurlsessiond, and construct artificial response events when the app is next brought to the foreground—breaking standard web platform streaming and interactive semantics.

Evidence

  • AppleURLSession.uploadTask(with:fromFile:) — Apple developer documentation establishing that background uploads require a file URL on disk.
  • AppleURLSessionConfiguration.background(withIdentifier:) — background transfer session configuration documentation.
  • WebKitAspect 4: The background NSURLSession fallback — analysis of how background NSURLSession bifurcates network stacks.

5Uploads: In-flight detection and assertion chains

When a web page submits a large form (such as a high-definition video or a photo attachment), or issues a fetch() or XMLHttpRequest with binary data, the browser engine must recognize that a data upload is in progress and track it until completion. In WebKit, this detection is embedded directly into the network loading infrastructure.

At the core request layer, WebCore's ResourceRequestBase::hasUpload() inspects the HTTP request body to check whether it contains file data (EncodedFileData) or blob data (EncodedBlobData). In the NetworkProcess, each connection to a web process manages its active network loads inside a NetworkResourceLoadMap. Whenever a loader with an upload starts, NetworkResourceLoadMap::add flags the connection as having active uploads and triggers hasUploadStateChanged(true). That notification is sent across IPC to the UIProcess via Messages::NetworkProcessProxy::SetWebProcessHasUploads. When loads complete or abort, NetworkResourceLoadMap::take re-evaluates whether any active load still has an upload, notifying the UIProcess when the count returns to zero.

Evidence

  • WebKitResourceRequestBase.cpp:569–579 — ResourceRequestBase::hasUpload() tests if any body element holds file or blob data.
  • WebKitNetworkResourceLoadMap.cpp:44–52 and :71–75 — adds and removes track active loaders and notify m_hasUploadChangeListener.
  • WebKitNetworkConnectionToWebProcess.cpp:150–153 and :237–241 — forwards upload status changes to the UIProcess with SetWebProcessHasUploads.
  • Commit033d8a856ac3 (2019-03-13) "Take UnboundedNetworking assertion when a file upload is in progress" — original implementation of the upload tracking pipeline.

Completing a web upload requires far more than keeping a raw network socket open. The page's JavaScript environment must remain alive to deliver chunked data or receive upload progress and completion callbacks; the networking process must continue sending packets; and the main application must stay alive so the user can return to a completed action. WebKit meets this requirement by keeping all three tiers runnable simultaneously.

When NetworkProcessProxy::setWebProcessHasUploads receives word that a WebContent process has started an upload, it instantiates an UploadActivity record and acquires three distinct ProcessAssertion instances with reason "WebKit uploads" and type ProcessAssertionType::UnboundedNetworking:

  1. UIProcess (the Safari browser app itself, identified via getCurrentProcessID()),
  2. NetworkProcess (the networking helper process, identified via *this),
  3. WebContent (the specific page process hosting the upload, identified via *process).

If another page in a different WebContent process also begins an upload, an additional assertion is registered for that second process in m_uploadActivity->webProcessAssertions. When all uploads for a given web process finish, its assertion is released. When zero uploads remain across the entire engine, m_uploadActivity is reset to std::nullopt, releasing the UIProcess and NetworkProcess assertions. If a WebContent process or the NetworkProcess crashes, cleanup handlers automatically teardown the associated assertions to prevent process leaks.

How Safari / WebKit does it

  • NetworkProcessProxy::setWebProcessHasUploads takes UnboundedNetworking assertions across UIProcess, NetworkProcess, and WebContent simultaneously under reason "WebKit uploads".
  • All three processes remain fully scheduled by the iOS kernel even when the user switches to other apps or locks the screen.
  • Assertions are automatically managed and released the moment the last upload transfer concludes.

What a BrowserEngineKit browser can do

  • No equivalent capability. BrowserEngineKit provides no API to request an unbounded networking assertion on any process.
  • A third-party browser can only request standard BEProcessCapability states (Foreground, Background, or Suspended), none of which permit indefinite execution.
  • When backgrounded, the host app and its extension processes receive only a standard ~30-second grace period before being frozen.

Evidence

  • WebKitNetworkProcessProxy.cpp:1763–1799 — setWebProcessHasUploads creates and manages the UploadActivity holding assertions for UIProcess, NetworkProcess, and WebContent.
  • Commit3a871e75aec1 (2020-04-17) "[iOS] Refactor WebKit uploads process assertion logic to minimize chances of leaking them" — unified UIProcess, NetworkProcess, and WebProcess assertions into UploadActivity.
  • DatasetEntitlements explorer › Process Lifecycle & Jetsam — analysis of private RunningBoard assertion capabilities in WebKit.

6The asymmetric solution: BEDownloadMonitor exists, but no "BEUploadMonitor"

The gap in background uploads is especially striking when compared to file downloads. In iOS 18.2, Apple introduced BEDownloadMonitor to BrowserEngineKit, creating a sanctioned public path for browser engines to perform background file downloads using their own networking processes.

As documented on the Aspect 2: The BEDownloadMonitor API analysis page, when an engine creates a BEDownloadMonitor, the system daemon (dasd, the Duet Activity Scheduler) takes a background assertion on the engine's networking process for the duration of the transfer. WebKit itself adopted this in October 2024 (commit b95877fdcedb), removing its own private download assertions in favor of BEDownloadMonitor.

However, no corresponding upload monitor exists. A search across WebKit's source code, BrowserEngineKit public headers, and Apple developer documentation reveals zero references to any BEUploadMonitor or similar upload-lifecycle API:

  • Downloads write incoming network data into a destination file URL in the user's Downloads folder. Once the HTTP response headers are received and the stream begins, the WebContent process is no longer strictly necessary; the system can track progress and placeholders via BEDownloadMonitorLocation.
  • Uploads originate from the web application: they require WebContent to feed data chunks, compute progress events, handle authentication challenges, or process responses. Keeping an upload alive requires keeping the entire multi-process pipeline (UIProcess + NetworkProcess + WebContent) running.

Because BrowserEngineKit provides no upload monitoring abstraction, WebKit continues to rely on its legacy, privileged UnboundedNetworking assertion chain in NetworkProcessProxy.cpp:1763–1799. For Safari, uploads keep running indefinitely in the background. For third-party engines, background uploads remain fundamentally broken.

Evidence

  • WebKitNetworkProcessProxy.cpp:1763–1799 — WebKit retains active UnboundedNetworking assertions for uploads on current main.
  • Commitb95877fdcedb (2024-10-07) "WebKit no longer needs to take unbounded network assertions on the network process for downloads … now that dasd is taking this assertion for us" — removed download assertions while leaving upload assertions untouched.
  • AppleBEDownloadMonitor — public BrowserEngineKit download progress monitoring API.
  • WebKitAspect 2: The BEDownloadMonitor API — detailed examination of BEDownloadMonitor mechanics.

7Tab survival: Jetsam and RunningBoard bands

Modern mobile web browsers run tabs in separate renderer processes to isolate memory and security contexts. On iOS, memory is aggressively managed by the Darwin kernel through a low-memory killer subsystem known as Jetsam (also referred to as memorystatus). Unlike desktop operating systems, iOS does not have traditional disk swap space. When physical memory becomes scarce, Jetsam terminates processes based on numerical priority bands, starting with the least important background processes or those that exceed their per-process memory limits.

When an inactive background tab's process is killed by Jetsam, the browser shell (the main UIProcess) detects the termination. Rather than crashing the entire browser, WebKit records the exit and sets a flag (m_shouldReloadDueToCrashWhenVisible). When the user subsequently taps back to that tab, the browser detects that the process is dead and reloads the URL from the network or disk cache. To the user, this tab discard appears as an unexpected blank screen followed by a page reload, often causing lost scroll position, lost form entries, and lost dynamic state in single-page web applications.

How Safari / WebKit does it

  • In WebPageProxy::dispatchProcessDidTerminate, when a WebContent process is terminated by Jetsam while its tab is invisible, WebKit avoids reloading immediately, setting m_shouldReloadDueToCrashWhenVisible = true.
  • When the user switches back to the tab, WebPageProxy::activityStateDidChange observes the tab becoming visible and invokes tryReloadAfterProcessTermination() to reload the page.
  • WebKit coordinates with system daemons to position active and background tabs in favorable Jetsam bands, delaying termination until other background apps or cached processes are reclaimed first.

What a BrowserEngineKit browser can do

  • The user experience symptom is identical: when an extension process is killed by Jetsam, the third-party browser's host app must detect the process termination and reload the web page when the user selects the tab.
  • Because third-party engines cannot request fine-grained Jetsam priority boosts from the kernel, their background tabs sit at standard extension priority and are vulnerable to being chosen earlier by Jetsam during memory spikes.

Evidence

  • WebKitWebPageProxy.cpp:14448–14457 — dispatchProcessDidTerminate marks m_shouldReloadDueToCrashWhenVisible = true when an invisible tab's process dies.
  • WebKitWebPageProxy.cpp:3651–3657 — activityStateDidChange intercepts view visibility changes to trigger tryReloadAfterProcessTermination() after a termination.
  • DatasetEntitlements explorer › Process Lifecycle & RunningBoard asymmetry — architectural overview of process lifecycle management differences.

Process priorities and lifecycles on Apple platforms are governed by RunningBoard, the system process-management daemon. RunningBoard translates high-level process assertions into XNU kernel scheduling states and Jetsam priority bands (ranging from active foreground apps down to idle cached processes). WebKit defines a suite of internal assertion types in ProcessAssertion.h to steer process priority.

Among these, WebKit includes two assertions tailored to Jetsam memory management: BoostedJetsam and BackgroundIdleJetsam. The BoostedJetsam assertion was introduced to elevate processes to a Jetsam band of at least 40, ensuring they are protected against premature termination even across suspension states. Conversely, WebKit uses BackgroundIdleJetsam (which RunningBoard internally maps to its "Suspended" attribute in the com.apple.webkit domain) to let prewarmed or cached background processes continue running work specifically in the lowest idle Jetsam band so the kernel reclaims them before hurting user-visible tabs. Taking assertions in the com.apple.webkit domain requires the private entitlement com.apple.runningboard.assertions.webkit.

How Safari / WebKit does it

  • ProcessAssertionCocoa.mm maps ProcessAssertionType::BoostedJetsam to RunningBoard name "BoostedJetsam" in domain "com.apple.webkit", and maps BackgroundIdleJetsam to RunningBoard name "Suspended".
  • In AuxiliaryProcessProxy, updateJetsamBoostAssertion() acquires a BoostedJetsam assertion for auxiliary processes to protect them from low-memory termination.
  • ProcessThrottler::assertionTypeForState dynamically switches background processes between Background and BackgroundIdleJetsam based on whether the process represents background activity or an idle cached process.
  • All auxiliary processes carry com.apple.runningboard.assertions.webkit, allowing RunningBoard to accept assertions in WebKit's private lifecycle domain.

What a BrowserEngineKit browser can do

  • Third-party browsers and their helper extensions do not carry com.apple.runningboard.assertions.webkit and are forbidden from acquiring assertions directly in the com.apple.webkit RunningBoard domain.
  • A third-party engine cannot ask RunningBoard for a BoostedJetsam assertion or an idle Jetsam band grant; any attempt to acquire private RunningBoard attributes triggers an invalidation error from the daemon.

Evidence

  • WebKitProcessAssertionCocoa.mm:338–384 — maps ProcessAssertionType values (including BoostedJetsam and BackgroundIdleJetsam) to RunningBoard names and the com.apple.webkit domain.
  • WebKitAuxiliaryProcessProxy.cpp:705–725 — setJetsamBoostEnabled() and updateJetsamBoostAssertion() taking the "Jetsam Boost" assertion.
  • WebKitProcessThrottler.cpp:283–295 — assertionTypeForState() selecting BackgroundIdleJetsam when background activities should run in the idle Jetsam band.
  • Commitc655abc1dd4a (2023-03-23) "Prevent WebContent Process from Jetsam" — introduces BoostedJetsam assertion to maintain a higher Jetsam band.
  • Commit23997cdd825d (2026-08-25) "Make prewarmed and cached processes run in idle jetsam band" — details how BackgroundIdleJetsam allows execution while remaining in the idle Jetsam reclaim band.
  • DatasetEntitlements explorer › com.apple.runningboard.assertions.webkit — entitlement granting access to WebKit's RunningBoard domain.

8Kernel freezer control and memory mitigations

Beyond RunningBoard, Apple's Darwin kernel provides a low-level system call, memorystatus_control, that interacts directly with kernel memory management and the iOS app freezer. The freezer is an operating system facility that compacts and freezes suspended process memory pages, reducing physical footprint so the processes can remain resident without triggering Jetsam kills.

WebKit's helper processes (WebContent, GPU, Networking, and Model) are signed by Apple with the private entitlement com.apple.private.memorystatus. In WebKit's source code, this entitlement enables WebContent processes to call memorystatus_control(MEMORYSTATUS_CMD_SET_PROCESS_IS_FREEZABLE, ...) in WebProcessCocoa.mm. When all pages inside a WebContent process are suspended, WebKit explicitly marks the process as unfreezable (because suspended pages are already pruned), but when active pages are present, it opts into kernel freezer management. The entitlement also authorizes querying and setting per-process Jetsam memory limits. Third-party engines cannot hold this entitlement and cannot issue privileged memorystatus_control commands.

How Safari / WebKit does it

  • Apple's build script process-entitlements.sh signs com.apple.private.memorystatus into WebContent (line 439), GPU (line 529), Model (line 586), and Networking (line 639) processes.
  • In WebProcess::updateFreezerStatus(), WebKit invokes memorystatus_control(MEMORYSTATUS_CMD_SET_PROCESS_IS_FREEZABLE, getpid(), ...) to inform the kernel whether the process is eligible for Darwin freezing.
  • Auxiliary sandboxes explicitly allow the SYS_memorystatus_control syscall and (allow system-memorystatus-control).

What a BrowserEngineKit browser can do

  • com.apple.private.memorystatus is an Apple-internal entitlement not granted to third parties or BrowserEngineKit extensions.
  • Third-party WebContent, Rendering, and Networking extensions cannot invoke privileged memorystatus_control commands to tune freezer status or manipulate Jetsam limits; they must rely entirely on OS-managed lifecycle transitions.

Evidence

  • WebKitprocess-entitlements.sh:439, 529, 586, 639 — grants com.apple.private.memorystatus to WebContent, GPU, Model, and Network processes on iOS.
  • WebKitWebProcessCocoa.mm:1159–1167 — updateFreezerStatus() calls memorystatus_control(MEMORYSTATUS_CMD_SET_PROCESS_IS_FREEZABLE, ...).
  • WebKitMemoryStatusSPI.h:39–55 — declarations for memorystatus_control, memorystatus_memlimit_properties_t, and freezer command constants.
  • Commitd8ce09ad934d (2019-03-22) "Implement WebProcess freezer opt-in completely on WebContent process side" — implements direct kernel freezer control in WebProcess.
  • DatasetEntitlements explorer › com.apple.private.memorystatus — full entitlement dossier.

To avoid Jetsam termination, an engine needs accurate visibility into its physical memory usage and remaining headroom. Fortunately, unlike process priority manipulation, memory observation is well-supported by public Darwin kernel and libdispatch APIs available to all iOS applications.

WebKit monitors system-wide memory pressure through a standard libdispatch event source (DISPATCH_SOURCE_TYPE_MEMORYPRESSURE) configured in MemoryPressureHandlerCocoa.mm, which delivers WARN and CRITICAL pressure notifications. To calculate remaining headroom before reaching its Jetsam ceiling, WebKit calls the public Mach kernel interface task_info(mach_task_self(), TASK_VM_INFO, ...) in AvailableMemory.cpp, reading phys_footprint and limit_bytes_remaining (mirrored in Darwin's public os_proc_available_memory() API). Furthermore, while WebKit's GPU process holds a private entitlement (com.apple.private.memory.ownership_transfer) to reassign graphics buffer accounting back to the client WebProcess, BrowserEngineKit provides an equivalent public path for third-party engines via task_create_identity_token and IOSurfaceSetOwnershipIdentity.

Parity in observation: Third-party engines have access to the same public memory pressure notifications and remaining memory calculations as WebKit, allowing them to detect impending low-memory situations and trigger internal pruning before Jetsam strikes.

How Safari / WebKit does it

  • MemoryPressureHandler creates a DISPATCH_SOURCE_TYPE_MEMORYPRESSURE dispatch source to receive kernel warnings (normal, warning, critical, process-limit-warning).
  • AvailableMemory.cpp calls task_info() with TASK_VM_INFO to read limit_bytes_remaining and physical footprint.
  • WebKit's GPU process transfers IOSurface memory attribution to the calling WebProcess using com.apple.private.memory.ownership_transfer.

What a BrowserEngineKit browser can do

  • Third-party engines can listen to the exact same DISPATCH_SOURCE_TYPE_MEMORYPRESSURE events and read task_info or os_proc_available_memory() to monitor memory headroom.

9The root cause: AssertionCapability limitations

BrowserEngineKit introduces a public abstraction called BEProcessCapability that allows host apps to request process lifecycle states for their extension processes. However, this abstraction is deliberately high-level. WebKit's own capability bridge, implemented in AssertionCapability.mm, reveals the strict boundary between what RunningBoard supports internally and what BrowserEngineKit exposes to third parties.

When WebKit runs with ExtensionKit capability management enabled, AssertionCapability inspects the requested assertion name. It only recognizes exactly three strings: "Suspended", "Background", and "Foreground". When WebKit encounters any specialized assertion type—such as BoostedJetsam, UnboundedNetworking, or MediaPlayback—AssertionCapability does nothing. In ProcessAssertionCocoa.mm, WebKit logs "Failed to create capability" and falls back to calling RBSAssertion acquireWithError:, which immediately fails for third-party apps lacking the private RunningBoard entitlement. A BrowserEngineKit browser simply has no API to express relative priority or custom Jetsam levels among its child processes.

How Safari / WebKit does it

  • Safari utilizes full RunningBoard services with Apple-private domain attributes (com.apple.webkit), allowing it to set granular lifecycle and Jetsam bands for each individual child process.
  • WebKit can independently adjust suspension timers, execution limits, and Jetsam boost properties without being constrained by the public BrowserEngineKit capability enum.

What a BrowserEngineKit browser can do

  • Third-party engines must manage process priority exclusively through [BEProcessCapability foreground], [BEProcessCapability background], and [BEProcessCapability suspended] (plus media playback and capture capabilities).
  • BrowserEngineKit provides no relative priority mechanism: an engine cannot mark one background tab as "recently used" and another as "stale", nor can it boost an active background tab's Jetsam band above the system default for background extensions.

Android comparison

Android does not freeze an app as soon as it leaves the foreground, and any app can keep a transfer running by hosting it in a foreground service (with a persistent notification) or by delegating it to the system DownloadManager. Chrome on Android uses both patterns, and alternative engines are free to do the same with their own network stacks. So on Android the question of "can my engine finish a download in the background with its own stack" has long had a public "yes"; on iOS the answer is "yes via BEDownloadMonitor on 18.2+, otherwise only by handing the URL to the system".

On Android, applications are not aggressively frozen immediately upon leaving the foreground. Background processes remain in cached or background states where active network sockets can continue transferring data, subject to standard Android Doze and App Standby battery optimizations.

For large or mission-critical background transfers, Android provides clear public mechanisms that any browser engine can leverage:

  • Foreground Services: A browser app on Android can elevate an ongoing upload by launching a Foreground Service (with android.permission.FOREGROUND_SERVICE_DATA_SYNC) displaying an ongoing notification in the notification shade. The browser engine's own network stack and process architecture remain fully active and unsuspended for the entire duration of the upload.
  • WorkManager / JobScheduler: For deferred or resumable transfers, Android offers system-managed background job scheduling that can execute tasks when network connectivity conditions are optimal.

Because alternative engines on Android can keep their own processes running via foreground services, background uploads do not suffer the instant freeze and socket termination experienced on iOS.

On Android, the operating system manages low-memory situations using the Low Memory Killer Daemon (lmkd), which terminates background processes according to an Out-Of-Memory score adjustment (oom_score_adj) ranging from -1000 to 1000.

Unlike iOS, Android provides public APIs that allow a browser host process to directly influence child renderer process priority. Through Android's Context.bindService() API, a browser can specify binding flags such as BIND_IMPORTANT, BIND_NOT_FOREGROUND, or BIND_WAIVE_PRIORITY. In Chromium on Android, the browser process actively ranks child renderer processes by Recency of Use (LRU): the most recently used background tab is assigned a lower OOM score than older tabs. As a result, Android's lmkd terminates the oldest, least-recently-used tabs first, preserving the user's active and recent tabs. On iOS, BrowserEngineKit offers no API to express relative priority among background extension processes to Jetsam.
