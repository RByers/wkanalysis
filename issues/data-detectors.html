1Data detection in page text: DataDetectorsCore scanning and DOM injection

When viewing a webpage in Safari, sequences of characters representing phone numbers, physical addresses, dates, flight numbers, or courier tracking numbers are automatically underlined and turned into interactive links. Users can tap or press them to trigger system actions like calling, adding to calendar, or navigating in Apple Maps, without the website author needing to format them as HTML links.

In WebKit, this scanning occurs inside the WebContent process (the sandboxed rendering process). WebCore executes DataDetection::detectContentInFrame, which builds a DDScanQuery from plain text fragments traversed across DOM nodes and passes it to the C-level private scanner API DDScannerScanQuery from DataDetectorsCore. The scanner reads system regex definition files located in /private/var/db/datadetectors/sys (specifically allowed by WebContent's sandbox profile). When matches are found, WebCore modifies the DOM tree directly: it wraps the matched character ranges in synthetic <a> elements tagged with attributes like x-apple-data-detectors="true", x-apple-data-detectors-type="telephone", and an internal URL scheme like x-apple-data-detectors://....

How Safari / WebKit does it

  • WebCore invokes private C functions in DataDetectorsCore (DDScannerCreate, DDScanQueryCreate, DDScannerScanQuery, DDScannerCopyResultsWithOptions) directly within the sandboxed WebContent process.
  • Matches are converted into synthetic DOM elements during page layout, styled with subtle native underlines (shouldUseLightLinks), and annotated with custom attributes to track result indexes.
  • Detects addresses, phone numbers, dates, calendar events, flight numbers, courier tracking numbers, and monetary amounts in a single pass.

What a BrowserEngineKit browser can do

  • Can perform text scanning on extracted DOM text using public Foundation API: NSDataDetector covers phone numbers, street addresses, dates/times, URLs, and transit/flight information (via NSTextCheckingTypeTransitInformation).
  • Shipment tracking numbers were historically not included in NSDataDetector; on modern targets, Swift's DataDetector provides .shipmentTrackingNumber, or the engine can run courier regex patterns.
  • The browser engine must implement its own DOM tokenization, text range resolution, and visual styling/link generation within its own render engine pipeline.

2Action UI: DataDetectorsUI, flight status, and package tracking cards

When a user taps or long-presses an underline created by a data detector, Safari does not simply navigate to a generic URL. Instead, it presents rich contextual system sheets: tapping a flight number shows an interactive flight card with route maps, departure and arrival times, and gate numbers; tapping a tracking number shows a delivery tracking card; tapping a date displays an inline calendar event creation sheet; and tapping an address shows an Apple Maps preview.

This entire interaction presentation is powered by DataDetectorsUI, a private system framework. In WebKit's UIProcess, WKActionSheetAssistant and WKContentViewInteraction consult [DDDetectionController sharedController]. For long-press gestures, WebKit calls [DDContextMenuAction contextMenuConfigurationForURL:... results:... inView:... context:...]. This returns a specialized DDContextMenuConfiguration (a private subclass of UIKit's UIContextMenuConfiguration) containing Apple's proprietary preview view controllers and contextual actions. If a user taps the preview, shouldExpandPreview modally presents the interactive full-screen system viewer.

How Safari / WebKit does it

  • WKActionSheetAssistant.mm queries DDDetectionController to obtain private DDAction objects and context titles for detected entities.
  • WKContentViewInteraction.mm delegates context-menu configuration to DDContextMenuAction, which creates native flight preview cards, Maps cards, and tracking view controllers directly.
  • Handles both immediate default actions (e.g. prompt to call) and rich multi-action context menus with animated previews.

What a BrowserEngineKit browser can do

  • Can construct standard UIKit context menus (via UIContextMenuInteraction) with custom UIAction items that invoke public URL schemes: tel:, mailto:, or http://maps.apple.com.
  • Can present public system view controllers for specific domains: EKEventEditViewController (EventKitUI) for calendar events and CNContactViewController (ContactsUI) for contacts.
  • Hard gap: Cannot display Apple's native flight status cards or package tracking preview cards. Those interactive view controllers are built directly into private DataDetectorsUI and have no public standalone equivalents in iOS SDKs.
  • UIKit's iOS 17 text item menu API (UITextItem and textView(_:menuConfigurationFor:defaultMenu:)) operates exclusively on native UITextView instances and cannot be attached to web content views.

3Live Text & Visual Look Up: VisionKit in web images

Apple's Live Text feature allows users to select, copy, and translate text embedded within images and video frames directly inside the browser. Visual Look Up extends this by identifying subjects such as dog breeds, plant species, famous landmarks, and art, showing a glowing "sparkle" badge that expands into an informative knowledge card.

In Safari, WebKit achieves this through a tight integration with private VisionKitCore SPI. The engine runs a dual architecture: First, the WebContent process captures bitmap snapshots of images (via ShareableBitmap) and sends them to the UIProcess. The UIProcess passes the bitmap to VKCImageAnalyzer, converts the returned VKCImageAnalysis via makeTextRecognitionResult into normalized word/line quads, and sends the structured data back to WebContent. WebCore's ImageOverlay.cpp then constructs a synthetic shadow DOM tree inside the <img> element containing transparent text nodes. This allows standard browser selection gestures, dictionary lookup, find-in-page, and accessibility screen readers (VoiceOver) to treat image text as native DOM text. Second, for interactive quick actions (QR codes, subject background lift, and Visual Look Up), WebKit installs a VKCImageAnalysisInteraction on the root content view. When a user looks up an image, WebKit invokes presentVisualSearchPreviewControllerForImage using QLPreviewController configured with the private appearance action QLPreviewControllerFirstTimeAppearanceActionEnableVisualSearchMode.

How Safari / WebKit does it

  • Runs optical character recognition via private VKCImageAnalyzer and injects transparent shadow DOM elements (ImageOverlay.cpp) directly behind images in the WebContent process.
  • Overlays live UI interaction using private VKCImageAnalysisInteraction with SPI callbacks like setAnalysisButtonRequiresVisibleContentGating:.
  • Visual Look Up is launched by presenting a QLPreviewController with private appearance mode flags (QLPreviewControllerFirstTimeAppearanceActionEnableVisualSearchMode).
  • Extracts subjects (background removal / Copy Subject) using private VKCRemoveBackgroundRequest.

What a BrowserEngineKit browser can do

  • Apple provides public ImageAnalyzer and ImageAnalysisInteraction in VisionKit.framework (iOS 16+). An app can pass a CGImage and attach the interaction to a UIView.
  • However, public ImageAnalysisInteraction is designed for single-view native image controls (like UIImageView). Mapping it over a multi-process browser compositor with dynamic scrolling, pinch-to-zoom, CSS transforms, and layer occlusion requires substantial custom overlay plumbing.
  • WebCore's transparent shadow DOM injection (making image text selectable via normal web text cursors) is an engine-level architecture that any third-party engine would have to reconstruct from scratch.
  • Hard gap: Third-party engines cannot invoke Apple's system Visual Look Up knowledge cards because the trigger is locked behind private QuickLook appearance action SPI.

4Writing Tools & system translation: Apple Intelligence integration

Apple Intelligence introduces Writing Tools in iOS 18, enabling users to proofread, rewrite in different tones (friendly, professional, concise), summarize, or convert selected text into lists or tables. In addition, Safari supports system-level full-page and selection translation, replacing foreign language text in-place.

WebKit's internal implementation of Writing Tools was built around private SPI in WritingToolsSPI.h (such as WTSession, WTContext, and WTTextSuggestion). For system translation, WebKit interacts with private TranslationUIServices (LTUITranslationViewController) and delegates text translation gestures to [_textInteractionAssistant translate:fromRect:]. However, Apple later introduced public developer APIs that change the outlook for alternative engines:

Modern API development: In iOS 18.2, Apple released UIWritingToolsCoordinator as public UIKit API. This class is specifically designed for custom text engines (such as third-party browser engines) to integrate Apple Intelligence Writing Tools into custom text views and editable DOM elements. Similarly, iOS 17.4 introduced the public Translation framework for running on-device translations.

How Safari / WebKit does it

  • WebKit integrates Writing Tools via private WritingTools.framework sessions (WTSession, WTCompositionSessionType, WTRequestedTool), coordinating proofreading suggestions and text animations between the UIProcess and WebContent.
  • Selection translation invokes private LTUITranslationViewController from TranslationUIServices.framework via WKTextInteractionWrapper.

What a BrowserEngineKit browser can do

  • Writing Tools: On iOS 18.2+, third-party engines can adopt the public UIWritingToolsCoordinator (and its delegate protocol). The coordinator accepts custom text contexts, communicates suggested rewrites, and manages Apple Intelligence text replacement lifecycle without private SPI.
  • Translation: On iOS 17.4+, third-party engines can use the public Translation framework (e.g. TranslationSession) to translate text programmatically. Presenting the translation in an inline context menu sheet similar to Safari requires engine-level UI construction.

5Link previews, QuickLook, and dictionary Look Up

When long-pressing a web link or selected word in Safari, users receive rich preview sheets: links display a live rendering of the destination page, selected words open dictionary definitions and Wikipedia summaries via "Look Up", and documents trigger QuickLook previews.

Standard file previews use QLPreviewController, which is a public framework. However, WebKit utilizes private SPI to enrich preview interactions: First, dictionary and Spotlight lookups use RevealCore (RVItem, RVPresenter, RVPresentingContext), an internal framework that coordinates dictionary definitions, Siri suggested websites, and knowledge cards. Second, rich link metadata previews leverage LinkPresentation (LPMetadataProvider and private SPI _startFetchingMetadataForURL:). While a third-party browser can present a secondary web view inside a UIContextMenuConfiguration preview provider to simulate Safari's link peek, it cannot access the private RevealCore service for system Look Up cards.

Open questions & confidence

  • Confidence: High. The mechanics of DataDetectorsCore scanning, WebContent DOM modification, and DataDetectorsUI context menu presentation are verified across multiple WebKit source files.
  • Evolving Public API Surface: The main-page description previously asserted that Writing Tools and system translation reach web content through private frameworks that third-party engines cannot use. Our analysis indicates this is partially outdated: Apple introduced the public Translation framework in iOS 17.4 and public UIWritingToolsCoordinator in iOS 18.2 specifically to allow custom text engines to participate in Apple Intelligence.
  • DOM-Level Live Text: While public ImageAnalysisInteraction exists in VisionKit for UIKit views, WebKit's unique approach of building a transparent shadow DOM overlay (ImageOverlay.cpp) allows standard web selection, copy, and accessibility tree integration. Third-party engines can technically replicate this DOM technique using raw OCR bounding boxes, but Apple does not provide a turnkey web-engine component.
  • Main-page text recommendation: We recommend updating the main-page summary to distinguish between features now supported via public API (Writing Tools on iOS 18.2+, Translation on iOS 17.4+) and the residual hard gaps that remain private: specifically Apple's interactive flight and shipment tracking preview cards in DataDetectorsUI and the Visual Look Up search mode in QLPreviewController.

Android comparison

On Android, system text intelligence is exposed through the public TextClassifier API (introduced in Android 8.1 / API 27 and expanded in Android 9 and 10). Any third-party browser engine can pass plain text to TextClassifier.classifyText() or TextClassifier.generateLinks() to detect entity types including phone numbers, physical addresses, dates, flight numbers, and URLs.

Crucially, unlike iOS's private DataDetectorsUI, Android's TextClassification returns public RemoteAction objects complete with titles, icons, and pending intents. This allows Chromium, Gecko, or any alternative engine to render the system-standard context menu actions (such as tracking a flight in Google or opening an address in Maps) with full system fidelity. For visual search on images, Android browsers typically invoke Google Lens or on-device ML Kit models through public intent interfaces.
