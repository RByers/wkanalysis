Can a BrowserEngineKit browser match Safari?

BrowserEngineKit (BEK) is Apple's iOS 17.4+ framework allowing alternative browser engines to run in sandboxed processes in the EU. While it provides essential multiprocess capabilities, structural platform asymmetries remain. The analysis below examines what capabilities are lost for developers and users, whether those same browsers have the capability on Android, and the strength of the source-code evidence.

Short answer: BEK covers the core of a browser engine (JavaScript JIT, multi-process isolation, basic scrolling and text input), so a third-party engine can render the web on iOS. But a set of Safari-only system privileges — above all Web Push, background downloads and uploads, Apple Pay, and several media and native-UI integrations — mean such a browser cannot fully match Safari, nor match its own Android version, and it runs inside a sandbox it can neither observe nor tune.

What BEK does provide

  • JIT compilation in WebContent processes via com.apple.developer.cs.allow-jit.
  • Multiprocess architecture (WebContent, Networking, and Rendering extension processes).
  • Basic scrolling and text interaction integration (BEScrollView / BETextInteraction).
  • A BEK or public equivalent exists for roughly 42% of the private APIs WebKit uses on iOS (847 of 2,014).
  • Storage and IndexedDB/Service Workers parity.

Background downloads In Safari, a large file download keeps going when the user switches to another app or locks the phone: WebKit keeps the browser app itself running for as long as a download is active (an "unbounded networking" system assertion, gated on the private com.apple.multitasking.systemappassertions entitlement). In a BEK browser, the app is suspended about 30 seconds after the user leaves it, which stalls the download. The download only finishes if the user comes back, or if the browser hands it off to iOS's public background download service (background NSURLSession). That service runs outside the engine, so it doesn't use the engine's own network stack, cookies or proxy settings. P2 High Yes (DownloadManager / foreground service) Entitlements › Process Lifecycle Entitlements › systemappassertions
Background uploads from web pages When a page is uploading (e.g. a video posted through a web form, fetch() or XHR), Safari keeps the browser app, its networking process and the page's process all running until the upload finishes, even if the user switches apps. In a BEK browser, the upload stalls once the app is suspended (about 30 seconds after the user leaves it), and the page usually sees a network error when the user returns. BEK only lets the browser keep its helper processes in the foreground, background (time-limited) or suspended states, so there's no option for "keep running until this network transfer finishes". iOS's public background upload service only takes whole files handed over by the app, so it can't carry an upload that page JavaScript is streaming. Background audio & calls Mostly achievable. Safari keeps itself and its GPU process running while a page plays audible media (a private "media playback" assertion), so music, podcasts and video audio keep playing with the screen locked or in another app. A BEK browser can get much the same result with public APIs: the app declares the standard background-audio mode, and BEK grants its media process a mediaPlaybackAndCapture capability. A web voice call that's already running can keep using the microphone the same way. The remaining gap is that Safari's GPU process holds a private entitlement to start microphone recording while in the background, which a BEK engine can't do. Tab survival under memory pressure WebKit can raise the priority of the processes behind active tabs so iOS's low-memory killer (jetsam) reclaims them later (a "boosted jetsam" assertion), and its helper processes hold the private com.apple.private.memorystatus entitlement to adjust memory-kill settings. BEK can't express either. Users may see a BEK browser's tabs reload, losing scroll position and unsaved form input, somewhat more often than Safari's when memory is tight. Passkeys & security keys Third-party browsers can use the public passkey/security-key APIs (ASAuthorizationController); only niche gaps remain (custom authenticator protocols, some attestation). P3 High Yes (Credential Manager) Services › webauthn
Developer tools (remote debugging) Safari's Web Inspector reaches pages through Apple's webinspectord daemon (private com.apple.private.webinspector.* entitlements). That daemon only talks to WebKit/JavaScriptCore, so a Blink or Gecko engine can't use it, and Safari for Mac can't inspect it. Nothing found in WebKit's sandbox or entitlements stops an engine from shipping its own tools instead, e.g. a Chrome DevTools Protocol server in the host app, reached over Wi-Fi or USB port forwarding. What's missing is ADB-style tooling: there is no public, zero-setup way to find and connect to a device over USB, and iOS suspends the browser when it goes to the background, which ends the debugging session. Browser (web) extensions Nothing technical stops a third-party engine from running WebExtensions itself, but it has to build the whole system (Chromium only ships extensions on desktop). WKWebView browsers get this for free from WKWebExtension, a public API since iOS 18.4. The real limits: (1) Safari Web Extensions bought on the App Store live inside other developers' apps, and only Safari can find and load them. Other browsers can only load extensions they bundle or download themselves. (2) Native messaging, where an extension talks to its companion app, goes through the private NSExtension API (extensionWithIdentifier:), so a third-party browser can't talk to another developer's native app. (3) Whether App Review allows extensions downloaded from a web store is a policy question not covered here. Analysis Scope & Limitations

These analyses examine WebKit's source (sandbox profiles, SPI allowlists, auxiliary daemons, entitlements). They do not examine BEK's own documentation/headers exhaustively, Apple's EU-only policy terms, or runtime behaviour of shipping third-party engines.
