Can a BrowserEngineKit browser match Safari?

BrowserEngineKit (BEK) is Apple's iOS 17.4+ framework allowing alternative browser engines to run in sandboxed processes in the EU. While it provides essential multiprocess capabilities, structural platform asymmetries remain. The analysis below examines what capabilities are lost for developers and users, whether those same browsers have the capability on Android, and the strength of the source-code evidence.

Short answer: BEK covers the core of a browser engine (JavaScript JIT, multi-process isolation, basic scrolling and text input, system-managed downloads, passkeys), so a third-party engine can render the web on iOS. But a set of Safari-only system privileges — above all Home Screen web apps with their own notifications and badges, Apple Pay on websites, Web Push to ordinary tabs, uploads that survive leaving the app, school and workplace filtering, web-to-app ad attribution, and DRM inside the engine's own media pipeline — mean such a browser cannot fully match Safari, nor match its own Android version, and it runs inside a sandbox it can neither observe nor tune. Of 23 candidate gaps examined, 13 are tracked below; the rest were found to be closed by public APIs or too small to matter and are listed separately.

How to read this site: each row below is a short, plain-language summary. What BEK does provide

  • JIT compilation in WebContent processes via com.apple.developer.cs.allow-jit.
  • Multiprocess architecture (WebContent, Networking, and Rendering extension processes).
  • Basic scrolling and text interaction integration (BEScrollView / BETextInteraction).
  • A BEK or public equivalent exists for roughly 42% of the private APIs WebKit uses on iOS (847 of 2,014).
  • Storage and IndexedDB/Service Workers parity.
  • System-managed background file downloads via BEDownloadMonitor (iOS 18.2+), the same path WebKit itself now uses on iOS (details).
  • Passkeys and security keys through the public AuthenticationServices APIs, which replaced WebKit's own WebAuthn process in 2022.
  • Screen Time web-content limits via BEWebContentFilter (iOS 26.2+), and background audio via the mediaPlaybackAndCapture process capability.

Home Screen web apps In Safari, a website added to the Home Screen behaves like a real app: its own icon, its own notification permission and identity, and its own badge. That depends on a Safari-only system daemon (webpushd) that can find, launch, notify and badge each installed web app through private interfaces and only accepts Safari's web-app host. School & workplace management: content filters & managed domains Schools and companies install filter apps that judge each page a device visits, and list "managed" web domains whose data must stay corporate. WebKit hands filters a per-page view (URL, response, content) through a private class and shows the filter's block page, and asks the private ManagedConfiguration framework whether a page is managed. A third-party engine's traffic reaches such filters only as connections by host name, with no block page, and it has no way to ask whether a site is managed. Screen Time's web limits are a separate mechanism that became public for BEK engines in iOS 26.2 (BEWebContentFilter). Web-to-app install attribution When someone taps an App Store ad in Safari and then installs the app, Apple privately tells the ad network that the click led to the install. A third-party browser can't register the click at all, so installs driven by its ads are invisible to advertisers; Apple's documentation says this works only in Safari, not even in WKWebView. Sandbox fragility & silent breakage Third-party engines run inside WebKit's own iOS sandbox profiles, which Apple adjusts roughly a hundred times a year (919 commits since 2014, 70% touching only sandbox rules), often in response to internal telemetry only Apple can see. When an iOS framework changes and needs a new sandbox exception, an engine can't ship the fix itself and can't observe the denial in production; it must wait for an iOS update. Eight commits so far have fixed rules that broke only third-party engines, and some permissions are revoked part-way through a process's life. Compositor performance & HDR WebKit composites web content through private cross-process CoreAnimation layer hosting and IOSurface ownership calls, backed by private QuartzCore entitlements. Rating Legend

  • Priority: A relative ranking (P1, P2, P3) of which gaps to close first, based on how much functionality is lost for web developers and end users. Every gap listed is a real loss of functionality compared with Safari; priority only orders them relative to each other.
  • Confidence: How well the source evidence supports the gap. Lowered when the gap is inferred from WebKit needing a private capability rather than from evidence that a third-party engine actually needs it (architecture-specific) or a public API alternative wasn't evaluated.

Analysis Scope & Limitations

These analyses examine WebKit's source (sandbox profiles, SPI allowlists, auxiliary daemons, entitlements). They do not examine BEK's own documentation/headers exhaustively, Apple's EU-only policy terms, or runtime behaviour of shipping third-party engines. Some gaps may be closed by public APIs we did not evaluate. Content is AI-generated and may contain errors.
